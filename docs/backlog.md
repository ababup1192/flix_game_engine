## 検査が測れない物は、たいてい描く側が言っていない（2026-08-14）

`lint-composition`（構図）と `bin/fge anim`（コマ間）の誤検出を追って分かったこと。
**`lint-composition` はこの後 2026-08-18 に削除した**（どの Makefile・フック・ゲートからも
呼ばれておらず、一度も走っていなかった）。下の表の「lint-composition」の行は、
いま動く道具ではなく、この調査のときの見取り図として読むこと。
**検査の道具と engine の API は独立ではない。** 検査が測れないのは道具の出来のせいではなく、
描く側が「何を描いたのか」を宣言していないことがほとんど。3 点セット
（**測りたい物 → 出す情報 → 測る道具**）で並べると、まだ情報が出ていない所が見える。

| 測りたい物 | いま出している情報 | 測る道具 | 足りるか |
|---|---|---|---|
| コマの回し方が破綻していないか | コマの画素だけ | lint-anim | **塞いだ**（sprite Doc の `loop`） |
| 意味色キーが色票から解けるか | *.palette.json / theme | lint-palette | 足りる |
| 面に階調があるか・矩形だけでないか | 画素と View のソース | lint-style / lint-view | 足りる |
| 主役が背景から分離しているか | シルエット PNG | lint-composition | **塞いだ**（面も写る silhouettePngWith） |
| 物が地面に埋まっていないか | シルエット PNG（塗りつぶし） | lint-composition | **足りない**（下記） |
| 層（奥・主役・手前）が分かれているか | z を手で分けた部位 PNG | lint-composition | 半分（`SilhouetteScope.ZWindow` で描き分けはできるようになった） |
| 当たり判定が絵と合っているか | hitbox.json と絵は別々 | 無し | **足りない**（絵と当たりを重ねて描き出す出力が無い） |

### 接地の検査は、いまの形では原理的に測れない

塗りつぶしのシルエットでは、奥へ退く地面は「地平線から画面下端までの黒い塊」になる。
列ごとの天面はその列のいちばん奥の縁であって、物が立つ表面ではない。奥へ退く面では
手前に立つ物ほど天面から下に離れるのが正しいので、**「埋まり」と「手前に立っている」を
画素からは区別できない**。坂と平らな床の区別も付かない。

出された 3 案の判断:

- **(c) 深度シルエット** — 割に合わない。深度の絵は「何が描かれたか」は言うが
  「その列の地面の表面はどこか」は言わない。曖昧さは残ったままで、描き出す費用だけ増える。
- **(b) 部位 PNG に奥／手前の別を持たせる** — z で既に分かる情報の言い換えにしかならない。
  `SilhouetteScope.ZWindow` で描き分けられるようになったので、これ以上は要らない。
- **(a) 天面だけを描き出す** — **横視点（地面が 1 本の線）でだけ正しい。** そこでは
  「列 x の地面の y」が 1 つに決まるので、天面の絵は本物の表面になる。
  奥へ退く面では「列 x の表面」が 1 つに決まらない（同じ列に手前から奥までの
  立ち位置が全部ある）ので、どんな絵を描き出しても答えは出ない。

**結論: 画素ではなく数を出す。** 描き出すときに `<名前>.layout.json` を並べて書く案を推す。
中身は「主役ごとの画面上の矩形と足元の点と zIndex」＋「ゲームが宣言した地面の線
（横視点なら列ごとの y・奥へ退く面なら Depth.orderAt に渡す足元の y）」。
検査はそれを読んで、足元 y とその物の zIndex が `Depth.orderAt` の順と食い違っていないかを見る
（これは**厳密に測れる**。画素から推し量る必要がない）。engine 側には
`Annotate`（注釈 JSON を書く）と `RenderLint` が既にあるので、置き場所はそのどちらか。
トリガー: **接地の検査を本気で効かせたくなったとき**（いまは lint 側が「測りません」と
1 行出して黙る形で、嘘をつかないぶん誠実）。

## ShaderGen のキャッシュのキーを短くする案（2026-08-17 に測って、やらないと決めた）

`LwjglLayer:1253` は毎フレーム `ShaderGen.compile(spec)` で GLSL 全文を組み、
**その全文をプログラムのキャッシュのキーにしている**。キャッシュに当たっても組み立て代は
払い済みなので、「テクスチャの本数 + `compileBody`」の短いキーに替えて、
全文はキャッシュを外したときだけ組む案を検討した。

**やらない。** 3 つの理由が独立に立っている。

1. **効果がしきい値に届かない。** 面 1 枚で 0.032ms/フレーム（実測 31.6µs）に対し、
   3-b の線は 0.8ms。**1/25**。「テンプレの Spec が貧弱だから小さいだけでは」を疑って、
   現実的に凝った Doc（binding 8 本・グラデ区切り 6 個・pow 4・Warp/Worley/Fbm/Glints/
   Ripples）でも測ったが、`compile` 1 回の割り当ては 314,848 → 386,112 バイトで
   **1.23 倍にしかならない**。Spec 非依存の prelude が固定費として支配するため。
   0.8ms に届くには凝った面が**同時に 20 枚**要る。
2. **壊れても退行検知に映らない。** `ShaderGen` を呼ぶのは `LwjglLayer` の 3 行だけで、
   リファレンス画像を描き出す headless の経路は `ShaderEval` を通るので**このコードを通らない**。
   キーの取り違えは「コンパイルは通る・テストは緑・絵だけ別物」に落ちる。
3. **正しさの説明をコメントに書けない。** 「なぜこの短いキーで足りるか」は `ShaderGen` の
   実装の説明（How）で、コメントの流儀に反する。しかも書く場所は `LwjglLayer` 側で、
   壊す人（`ShaderGen` にノードを足す人）が開かないファイルになる。

**替わりにやったこと**（同じ回で実施・出力はバイト同一）:
`preludeSource` の 119 個の `+` 連鎖と、`bindingPrelude` / `gradientExpr` / `powProduct` の
文字列蓄積を 1 回組みへ。`compile` 1 回の割り当ては 314,848 → **121,608 バイト（−61%）**。

**関連する未着手**: このキャッシュ（`LwjglLayer:480`）は `Map.insert` だけで**消す口が無く、
寿命はプロセスと同じ**。色や位置は GLSL にリテラルとして埋め込まれるので、Studio で
スライダーを動かすと値ごとに別のプログラムが増えて解放されない可能性がある。
Studio が実際にその経路を毎フレーム通るかは未確認。

## Flix の宣言を字で読む実装が 3 本ある（2026-10-21 の doc-refs で 3 本目）

- **今の 3 本**: `go/internal/flixdecl`（pub の宣言と本文。api-digest・f32 が使う）・`go/internal/engineuses`
  （fpkg の木の一番外の pub の名前。`use fge::{…}` を足す）・`go/internal/docrefs/flixindex.go`（mod・def・enum・case・
  eff・trait・struct・record の欄の完全な名前。文書が指す名前を引く。flix.jar の標準ライブラリも同じ口で読む）。
  コメントと文字列を空白にする所（`stateshape.Blank`）だけは共有しているが、括弧の深さ・入れ物の積み方・
  `instance` の外し方はそれぞれが持つ。
- **まとめる形の候補**: flixdecl に「入れ物の木（mod > enum/eff/trait/struct > case/def/欄）と各宣言の pub・位置」を
  返す 1 つの口を置き、3 本はその木から要る物だけを取る。flixlint の索引（`bin/fge refactor` が作る
  build/refactor/spans-resolved.tsv）がある所では木の代わりにそれを読む。
- **トリガー**: 3 本のどれかで Flix の構文の読み違い（新しい宣言の形・入れ子の数え違い）を直す時。
  その時に直す所が 3 か所に分かれていれば、直すのと一緒にまとめる。
