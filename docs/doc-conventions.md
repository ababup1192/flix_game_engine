# Doc 規約 — ゲームデータ JSON の共通ルール

このエンジンのゲームデータ（キャラ・テーマ・光・シェーダーなど）は、すべて
「Doc」と呼ぶ JSON ファイルで持つ。Doc は種類が違っても**外側の形は全部同じ**。
だから一度覚えれば全部読めるし、エディタ・ホットリロード・テスト・AI 生成が
どの Doc にも同じやり方で効く。

この文書はその「外側の形」を決める規約。**新しい機能はここに従う Doc を
1 つ足す形でだけ増やす。外側の形そのものは変えない。**

## 命名

| 場合 | ファイル名 | 例 |
|---|---|---|
| 同じ種類のファイルが複数ある | `<名前>.<種類>.json` | `grass.theme.json` / `cave.light.json` / `b1.dungeon.json` |
| プロジェクトに 1 つだけ | `<種類>.json` | `characters.json` / `hitbox.json` |
| スキーマ（種類ごとに 1 つ） | `<種類>.schema.json` | `theme.schema.json` |

## 外形 7 点（すべての Doc が守ること）

1. **`version` を持つ**（整数）。将来形を変える時の移行の目印。
2. **スキーマを持つ**（`<種類>.schema.json`）。エディタのフォーム生成・
   起動時の検証・AI がデータを書く時の仕様書、の 3 役を 1 枚で担う。
3. **読み込みは fail-open**。書き損じや欠けは既定値へ落とす。色 1 つのミスで
   画面を壊すより、保存即反映で直せる方を選ぶ。**既定値で続けたら 1 行言う・続けるか
   止めるかは呼ぶ側が選ぶ**（3 つに分ける決まりは [docs/error-handling.md](error-handling.md)）。
4. **`title` を持つ**（人が読む短い表示名。ひらがな・カタカナ・漢字でよい）。
   ファイルが増えると `town_ground.sprite.json` のような機械の名前では中身を思い出せない。
   エディタの目次は **`title` → 無ければファイル名 → ファイル名が被ったらフルパス**で出す。
   **生成物には書かない**（`*.palette.json` のように出力とバイト比較している Doc は、
   手で足すと検査が落ちる。書くなら生成する側が出す）。
5. **`note` フィールド歓迎**。人間と AI のためのメモを一級として許す
   （パーサは黙って無視する）。
6. **project.json の `editor.resources[]` が唯一の登録先**。
   `{ id, pattern, title, schema }` を宣言すると、エディタの目次に並ぶ。
   キー名は `schema`（`schemaPath` ではない — 間違えると黙って sibling 規約へ
   落ちて迷子になるため、未知キーはエディタが警告する）。
   宣言していない Doc はエディタに現れない（それだけ。ゲームは動く）。
7. **保存で即反映・スナップショットでテスト可能**。ゲームは `Controls.docTable` の `Resources.reloadRow` で Doc を
   監視し（Doc は World ではなく Res に置く）、編集は走っているゲームにその場で映る。Doc → 絵/トレースは
   決定的なので、スナップショットのバイト一致でテストできる。

## 大きさの目安（超えたら割る）

Doc は放っておくと「何でも入れる引き出し」になる。エディタは 1 セクション = 1 タブで出すので、
数十個の設定を平らに並べると**タブが横スクロールして、値 1 つ触るのにクリック 1 回**になる。
実装の天井（タブは横 1 列・フォームは縦 1 列・参照解決と検査は 1 階層しか追わない）から、
次を目安にする。

| 物差し | 目安 | 超えたら |
|---|---|---|
| 1 Doc が持つ関心 | **1 つ**（いつ読み直したいかが同じ物だけ） | Doc を割る |
| タブの枚数 | **8 枚以下** | group で束ねる → それでも多ければ Doc を割る |
| 1 タブのフィールド数 | **15 個以下** | group を分ける |
| 1 Doc のスカラー総数 | **30 個以下** | Doc を割る |
| 入れ子の深さ | **2 階層まで**（record 1 階層、または list の item 1 階層） | 形を見直す。3 階層目は参照解決も検査も効かない |

**同じ接頭辞のキーが 5 個以上並んだら割れの合図**（`shade*` `shadow*` `*Grain*` のような列は、
たいてい別の関心が紛れ込んでいる）。「同時に読み直したいか」で切る — 絵の仕上げと
手触りの数値は、触る目的が違うので別 Doc にする。

### 一覧を持つ Doc（`sprite.json` / 配置 / 敵表）の目安

上の表はつまみ（`sections` に並ぶ値）の物差しで、**中身が増えていく一覧には効かない**。
一覧型は次で見る。

| 物差し | 目安 | 超えたら |
|---|---|---|
| 1 ファイルの項目数（絵の枚数・配置の個数） | **16 個以下** | ファイルを割る |
| 1 ファイルの大きさ | **20KB 以下** | ファイルを割る |
| 見出し（`group`）1 つに入る項目数 | **8 個以下** | 見出しを分ける → それでも多ければ割る |

**割る線は「同じタイミングで描き直すか」。** 地面のタイルと建物と人は、直す時が違う。
`town_ground` / `town_water` / `town_build` のように分ければ、1 ファイル 12〜13 枚に収まる。

**遅くなる理由は JSON の読み書きではない。** 50KB の `sprite.json` でも 1 打の
書き戻しは 0.64ms、`JSON.parse` は 0.07ms で誤差（2026-08-17 実測）。効くのは
**エディタが一筆を確定するたびに、その Doc の項目を全部組み直す**所。同じファイルに
無関係な絵が 40 枚居れば、その 40 枚の分だけ 1 筆ごとに鈍る。だから
**「重いから割る」ではなく「同時に触らない物を同居させない」**と考える。

**`group` は割らない言い訳ではない**（下の節と同じ）。見出しを付けても、
1 ファイルに 41 枚あれば 1 筆ごとに 41 枚を組み直す事実は変わらない。

## タブの束ね方（`group`）

単一値（`kind: "value"` / `"field"`）のセクションは、**`group` に同じ名前を書くと 1 枚のタブに
束ねて表として並ぶ**。書かなければ「基本」タブへ入る。

```json
"sections": {
  "walkSpeed": { "kind": "value", "type": "float", "label": "歩く速さ(px/秒)", "group": "動き" },
  "runSpeed":  { "kind": "value", "type": "float", "label": "走る速さ(px/秒)", "group": "動き" },
  "wakeHour":  { "kind": "value", "type": "int",   "label": "起きる時刻",     "group": "時間と暦" }
}
```

- **JSON の形は変えない**。`group` は見せ方だけの指定で、値は今までどおり文書直下に書き戻る。
- 一覧を持つ種類（`catalog` / `list` / `record`）は束ねない。追加・削除・並べ替えがタブ単位のため。
- 古いエディタは未知のキーとして黙って無視する（前にも後ろにも互換）。

**`group` はタブが溢れたときの応急処置であって、Doc を割らない言い訳ではない。**
まず「1 Doc = 1 関心」で割れないかを考える。

## 増えるデータは一覧（`catalog`）にする

色票のように**後から名前を足したくなる**データを、フィールドを 1 つずつ宣言する形で持つと、
1 つ増やすたびにコードとスキーマの両方を書き足すことになる。名前で引く一覧にすれば
JSON に 1 行足すだけで増え、エディタから追加・改名もできる。

```json
{ "version": 1, "colors": { "grass": { "hex": "#5c9648" }, "soil": { "hex": "#8a6a45" } } }
```

読む側は「名前 → 値」の Map で受け、**知らない名前は目に見える色（マゼンタ）へ落とす** —
打ち間違いが黙って既定色になると気付けない。

## ドット絵の意味色キーは色票に実体を置く

`*.sprite.json` の `legend` に書いた名前（`"a": "accent"` など）を、コードの中だけで
導いてはいけない（つや・影のような派生色も同じ）。エディタが名前を実色に解ける道は
**`*.theme.json` のトップレベルの名前・sprite Doc の `paletteFile` が指す色票・
sprite Doc 直下の `palette`** の 3 つだけで、どれにも無い名前は仮色で塗られる。
編集画面と実機で配色が食い違い、しかも見ただけでは気付けない。

派生色をコードで計算しているなら、その結果を**色票 JSON として書き出し**（`make` の
生成ターゲットにして、元の色を変えたら生成し直す）、sprite Doc の `paletteFile` でそれを
指す。書き出した色票と実機の色が一致することをテスト 1 本で pin しておけば、
色票の生成忘れに気付ける。書き出しは `PaletteExport.write`（engine_world）に一本化してあり、
ゲーム側に書くのは「意味色キーの列」と resolver だけでよい。

`make lint-palette` が `templates/` の全 sprite Doc を検査し、
解けない名前を挙げる。

## 配置 Doc は画面 px を持たず world 座標だけを持つ

物をどこに置くかを書く Doc（`*.scene.json` など）に、**画面の px を書かない。
書くのは world 座標だけ**で、画面のどこに出るかは写し方（`ViewProjection`）が決める。

理由は「直しが機械で書けるかどうか」に尽きる。人が絵を見て言うことは、たいてい
「この岩、もう少し左へ」の形をしている。Doc が world 座標だけを持ち、画面 px との
往復が 1 か所にあると、これを **`ViewProjection.inverseOf` → `toWorldDelta` に通すだけで
「`place[7].x` を 0.62 → 0.589 へ」に翻訳できる**。画面 px を Doc に書いてしまうと、
どの数字が効いているかが視点の実装に散らばって、この翻訳が書けなくなる。

視点ごとに world の意味は違ってよい（決めるのはゲーム。engine は式だけを持つ）:

| 視点 | world の意味 | 画面から戻せるか |
|---|---|---|
| 横から（`side`） | `(x, y)` = world 単位（1 world = `zoom` px。`center` を画面の中央に映す） | 戻せる |
| 見下ろし（`topdown`） | `(x, y)` = 床の world 単位（持ち物は `side` と同じ） | 戻せる |
| 斜め見下ろし（`quarter`） | `(x, y, h)` = タイル座標 + 高さ | 戻せる（高さ `h` を渡せば一意） |
| 一人称（`firstPerson`） | `(x, y)` = 格子の連続座標 | **戻せない**（下記） |

一人称だけは例外で、画面の 1 点に当たる world の点が奥行きぶん無数にある
（透視除算が 2 つの数を 1 つに潰す）。ここで「床の高さを 1 つ決めた戻し方」を
規約に混ぜると、床の上に無い物で嘘になる。代わりに `ViewProjection` は
**`firstPersonOf` で持ち物を 1 回取り出してから `yawOf`（正面から何度ずれているか）・
`distanceOf`（何マス先か）・`visibleFraction`（画面にどれだけ入っているか）** を読む。「中央へ寄せたい」
「もっと手前に」は、この 3 つを見て Doc の座標を動かす。

**逆変換の書けない写し方を土台に入れない。** 入れた時点で、上の翻訳が
その視点だけ成立しなくなり、目録（`RenderManifest`）の `src` も指す先を失う。

## 大きさは Doc が割合で持ち、描き手が整数へ丸める

配置 Doc（`*.scene.json` など）に物の大きさを書くとき、**`scale: 2` のような画素の倍率を
書かない。`size: 0.6` のような「基準に対する割合」か world px を書く。**

理由は 2 つ。

- **倍率は描き手の解像度に縛られる。** 同じ配置 Doc を 8px タイルの描き手と 16px タイルの
  描き手が読むと、`scale: 2` は片方で 16px・もう片方で 32px になる。Doc は「この物は
  周りの何割の大きさか」を言いたいのであって、何画素かを言いたいのではない。
- **画素の格子に乗る絵で非整数拡大をしてはいけない。** 1.5 倍すると 1 画素が 1px と 2px に
  割れ、絵の中で画素の大きさが不揃いになる（ドット絵が「壊れて」見える一番の原因）。
  だから `PxSprite` の scale は整数のままにしてある — これは制限ではなく規約。

**割合から画素の倍率への丸めは描き手（View）の仕事。** 描き手は自分の基準（1 画素が
画面の何 px か）を知っているので、`Num.roundInt(base * ratio)` を 1 以上に丸めて
`PxSprite` へ渡す。画素の格子に乗せない描き手（図形・`ShaderDoc` の面）は丸めずに
そのまま割合を使ってよい — 丸めが要るかどうかも描き手ごとに違う、という話。

## 宣言し忘れは検査が知らせる

スキーマに書き忘れたキーは、**ファイルには残るのにエディタから触れなくなる**。
エディタは文書直下のキーを見て「スキーマが "x" を宣言していません」と知らせる
（`version`・`note`・`//` で始まるキーは規約で認めた物なので数えない）。

## データの流れ（Doc がゲームに効くまで）

```
*.kind.json → load（起動時に値へ）→ Res（Doc と、Doc から作る物）──読む──▶ 系・View
                     ↑ 保存を Controls.docTable の Resources.reloadRow が拾って Res を替え、settle で World を収める
                                          seed（純関数・一度きり）→ World（遊びの状態の唯一の権威）
```

Doc は「初期値と見た目の宣言」まで。Doc そのものは World に置かず Res に置き、実行中の状態は World だけが持つ
（`flix-conventions.md` の「World は遊びの状態だけを持つ」）。
振る舞い（ルール・生成・物理）はコードで書く — Doc に振る舞いは入れない。

## 新しい Doc を足すときのチェックリスト

- [ ] ファイル名は命名表に従っているか
- [ ] `version: 1` があるか
- [ ] `title`（人が読む短い表示名）を書いたか（生成物には書かない）
- [ ] `<種類>.schema.json` を書いたか
- [ ] 読み込みを 3 つに分けたか（`load*` が `Result` を返し、フォールバックは `loadOr` へ）
- [ ] 既定値で続けたときに 1 行言うか（[docs/error-handling.md](error-handling.md)）
- [ ] project.json の `editor.resources[]` に宣言したか
- [ ] Doc を Res の欄に置き、`Controls.docTable` に `Resources.reloadRow` の行を足したか（即反映が欲しい場合）
- [ ] Doc → 出力（絵・値）を pin するテストを 1 本書いたか
- [ ] 大きさの目安に収まっているか（タブ 8 枚・1 タブ 15 個・総数 30 個・深さ 2 階層）
- [ ] 単一値が 5 個以上あるなら `group` で束ねたか
- [ ] 後から名前が増えるデータは `catalog`（名前で引く一覧）にしたか
- [ ] ドット絵なら `make lint-palette` が通るか（`legend` の名前が色票にあるか）

## 任意の推奨規約：いま画面に出ている Doc を名乗る

ゲームは表示中の Doc が変わったとき、`debug/active-docs.json` に
「宣言 id → いま読んでいるファイル」を書いてよい（任意・変化時のみ）:

```json
{ "active": { "dungeon": "assets/b1.dungeon.json", "theme": "assets/grass.theme.json" } }
```

エディタはこれを見て「いま画面に出ているファイル」に 🎮 印を付け、
表示中でないファイルを編集している時に注意を出す。ファイルが無ければ
エディタは何も出さない（付けるかどうかはゲームの自由）。

## スキーマの書き方（sections 方言の細かい取り決め）

- **スカラー型は `text` を標準**にする。schema の `kind: "field"` と `"value"` は
  同義（どちらも「スカラー 1 個のセクション」）。**`@参照`（テーマ色などを名前で
  引く）を書く欄は `color` でなく `text`** にする — color ピッカーは `#rrggbb` の
  固定色しか表せず、`@wall` のような参照を書けないため。
- **terrain の `entries[].char` は表内で一意**が契約。重複していたら先勝ち
  （先の宣言が有効・後は捨てる）で decode する（壊れ扱いにせず静かに受け入れる = fail-open）。

## 良いお手本

flix_ge_dungeon の assets/ がこの規約の実例になっている:
`characters.json` + `characters.schema.json`（キャラ）、`*.theme.json`（地形の
見た目）、`*.light.json`（灯り）、`*.dungeon.json`（フロア）、`sprites.json`
（飾り）、`*.shader.json`（水・マグマの面）。project.json の editor 宣言と
セットで、エディタ・ホットリロード・テストが全部この形の上で動く。

`*.terrain.json`（セル文字→質感の表。色は `#rrggbb` か `@キー` のテーマ参照）は
**このリポジトリ内に見本が無い**。書き方は `engine_world/src/TerrainDoc.flix` の
冒頭 doc コメントと `engine_world/test/TestTerrainDoc.flix` を見る。仕組みは
[dual-grid.md](dual-grid.md)。

## 文書（.md）と .flix のコメントの中で名前・パスを書く記法（doc-refs が読む）

ここまでは JSON の Doc の規約。この節だけは文書（`docs/**/*.md`・`NOTES.md`・`AGENTS.local.md`・agents-pack）の書き方で、
`bin/fge doc-refs`（`make lint-doc-refs`・コミットでは触った .md を precommit が見る）がこの記法を読む。
文書ごと・1 か所ごとに外す道は無いので、今は無い物を書くときは下のどれかで書く。印は `bin/lint-rules/doc-refs.json` が持つ。

| 書きたい物 | 書き方 | 例 |
|---|---|---|
| 今ある名前・ファイル | そのまま ` ` の中か表に | `SortingLayer.compose`・`docs/flow.md` |
| これから作る名前（計画の文書） | 名前の ` ` の直後に `（予定）`（表は語の直後） | `World.arenaOf`（予定）・`src/Arena.flix`（予定） |
| 消した名前（記録として残す） | `~~ ~~` の消し線で囲む | ~~`ActiveDocs.step`~~ は消した |
| エンジンの文書からゲームの側の物 | 頭を `<ゲーム>/` にする（ゲームの名前を書かない） | `<ゲーム>/bin/video-status.py` |
| ゲームの文書からエンジンの文書 | 直前に「engine の」 | engine の `docs/pacing.md` |
| 誤りの文（コンパイラの出力）の引用 | ` ` の中の名前を `'…'` で囲んだまま写す | `Undefined name 'App.run'` |
| 仮の字 | `<名前>`・`*`・`…` | `e2e/<名前>.flow` |

- 計画が済んで名前ができたら `（予定）` を外す（残しても止まらないが、読む人には古い印になる）。
- Flix の標準ライブラリの名前（`Clock.runWithIO`・`List.map`）はそのまま書く。doc-refs は `bin/flix.jar` の
  `src/library` から引く（engine の `Clock` と同じ頭でも標準に在れば通る）。
- 頭の 5 行に「手で直さない」（か「手で編集しない」・`DO NOT EDIT`）と書いた文書は生成物として見ない。
  直すのは作る元（`bin/fge check codes --md` なら flixlint の go/checkres の表）。
- 古い記録の文書（`notes/<年-月>.md` など）は文書ごと `<ゲーム>/bin/lint-rules/doc-refs.local.json` の skip へ。
- `.flix` のコメント（`///` と `//`）も同じ記法で読む。拾うのは ` ` の中と、地の文の語のうち `Mod.name`・`/` を含むパス・
  `path:行` の形の物だけ（ほかの地の文は見ない）。`.flix` の物は上限で数える: `make lint-doc-refs` はリポごとの
  `lint/doc-refs/flix.json`（`{"limit": N}`。無ければ 0）と比べ、増えたら止め、減ったら上限を下げるまで止める。
  `lint/limits/` には置かない（flixlint の上限の置き場で、知らない id の上限を flixlint が止める。古い置き場に残っていれば
  doc-refs が移すよう言って止まる）。
  コミットでは触った `.flix` の、HEAD の中身より増えた物だけを止める（古い件で関係の無いコミットを止めない）。
