# テストの設計

Flix の書き方は `flix-docs` スキル。**例は同じフォルダの `reference.md`** — 困ったらその節だけ引く:

| 困った時 | `reference.md` の節 |
|---|---|
| 複数の値を 1 回の assertEq にまとめる・期待形にだけ match する | 「1 テスト 1 アサートと bug!」 |
| 副作用（Clock・Fs など）を差し替える | 「Effect ハンドラのモック」 |
| セクションの区切りとテストの上のコメント | 「区切りと意図コメント」 |
| 入力と期待値の数の選び方 | 「区切りの良い数」 |

## 何をテストするか

テストするのは 2 つだけ。

1. **ゲームのルール・進行・収支**（状態遷移・境界条件・勝敗や資源の帳尻）。クリック当たりの有無（この状態では押せない）もルールに入る
2. **JSON（Doc）とプログラムの橋渡し**

テストしない物: モーション・表示タイミング・座標の丸写し（演出の戻りはスナップショットと目視の仕事）、
initialState の値の写し、getter/setter の恒等・委譲だけのラッパ・型が保証している事。
書くのは、操作を組み合わせた帰結・境界条件・状態遷移の順序・不変条件・過去にバグった条件。
基準は「読んだ人がその関数の性質を分かるか」。同じ事を確かめるテストは 1 本にまとめる。

新しいモジュール・公開関数を足したら、同じコミットで `@Test` も足す。

## 期待値は Doc から導く

Doc に出した数を使う所は、**数のリテラルを貼らず Doc 経由の式で書く**（`50.0` ではなく `Prologue.dayLen(d())`）。
JSON の既定値を調整してもテストが壊れないようにするため。

## 橋渡しテストは 1 Doc につき最大 3 本

1. 壊れた JSON → 既定値に落ちる（fail-open）
2. 1 フィールドだけ上書きした JSON → その値が入る
3. rows（可変長の欄）の長さに追随する

デコーダを細かく確かめるのは共通層（JsonCodec）で 1 回だけ。Doc ごとに繰り返さない。

## 1 本のテストの形

- **公開 API と本物の構築関数を通す。** テスト用に内部の状態を手で組まない（構造そのものを見るテストはローダ／ビルダーを直接呼ぶ）
- **担当外の値を一緒に見ない**（物理のテストでアニメーションを見ない）
- 名前は「対象 + 振る舞い」（`testXxxFallsWhenYyy`）。`@Test` の上に `///` で何を確かめるかと数の根拠を書く
- **1 テスト 1 アサート。** 複数の値はタプルか List にまとめて 1 回の `assertEq`。
  例外は、純粋な数のユーティリティで成分ごとに独立に確かめる意味がある時だけ（場面・状態のテストは必ずまとめる）
- 本体に `if` や多分岐の `match` を書かない。期待の 1 形だけに match し、来てはいけない形は `bug!("...")`（スキップや空の assert にしない）
- 誤差の出る計算（正規化・三角関数・積み重ね）だけ `Float64.abs(actual - expected) < epsilon` を `assertTrue`。epsilon は意味で選ぶ（位置 0.001・長さ 0.01）。決まった結果は `assertEq`
- `@Test` の戻り値は `Unit`。エフェクトはシグネチャに書くだけで、ハンドラは書かない

## テストにロジックを書かない（ヘルパーも）

テストのロジックが正しいかを、また別のテストで確かめることになる。次が出たら立ち止まる:
`List.fold` で期待値を組む・`List.map` / `filter` で入力を加工する・`if` で期待値を出し分ける・
自前の再帰で結果を出す・ループで何ステップも進めて値を集める。

- 入力も期待値も直接書いた具体値。「N ステップ進める」はステップを書き並べるか、対象の API に N 回進める関数を作る
- ヘルパーは**副作用のモック**と**値の取り出し・タプルへの変換**だけ。計算は対象モジュールへ押し戻す
- 判断: そのヘルパーが間違っていたらテストが嘘になるか。なるならロジックが多すぎる

## モックと共通ヘルパー

- 副作用は **effect 多相のヘルパー**（`Unit -> a \ ef + Clock` を受けて `a \ ef` を返す）で差し替える。テスト本体に `run ... with handler` を直に書かない
- 複数のモックは入れ子の `run` にせず、ヘルパーを重ねて呼ぶ（`withMockA(() -> withMockB(() -> ...))`）
- 2 つ以上のテストファイルから使うモック・ファクトリ（`testXxx()`）・タプル変換（`xxxToTuple`）・1 歩進める薄いラッパは、
  **集約用のテストファイル 1 か所**に置いて使い回す。1 ファイルの中だけで使う物はそのファイルに置く

## 数の選び方

Doc に由来しない入力と期待値は、暗算で追える区切りの良い数（0・10・50・100・0.5・1.0）にする。
期待値が入力から手計算で出るように入力を選び、半端になる時は根拠の式をコメントに書く。

セクションは大きな ASCII コメントで区切り、「初期状態 → 単発の操作 → 操作の組み合わせ → 状態遷移」の順に並べる。
