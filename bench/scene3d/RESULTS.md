## draw call が分かれた理由・診断の重さ（0.95.0 の後・P0 の後半）

測った日 2026-11-14 / 同じ機械（Apple M4 Pro・GL）/ 垂直同期なし・音なし。基準（`bench/baseline/0.95.0/`）は取り直していない。
engine は「draw call がまとまらなかった理由を診断に出す」「GPU の時間の query を 16 コマに 1 回に間引く」の 2 つを入れた物（直す前 = main の 0af3e8b5）。

### draw call が分かれた理由（`draw3d_breaks`。1 コマの値・区間の中央値。3D は draw call 1 つを 1 つの理由に数えるので合計 = draw call）

| 条件 | draw call | 分かれた理由 |
|---|---|---|
| room | 10 | mesh 10 |
| field n=12000 shapes=1 mats=1 | 2 | material 1 / mesh 1 |
| field n=12000 shapes=16 mats=16 | 257 | material 16 / mesh 241 |
| field n=12000 shapes=each mats=1 | 12001 | material 1 / mesh 12000 |
| field n=12000 shapes=1 mats=1 alpha=10 | 1202 | transparent 1200 / material 1 / mesh 1 |
| field n=12000 shapes=1 mats=1 shadow=1 | 4 | shadowPass 2 / material 1 / mesh 1 |

- draw call の数は基準の表と同じ（10・2・257・12001・1202・4）。
- 形 16 × 材質 16 は、前の batch と材質が違う draw call が 16・材質は前と同じで形が違う draw call が 241。
  数え方の決まり（先に当てはまった 1 つ・`material` は `mesh` より先）は `FrameDiagnostics.Scene3dBatchBreaks` の doc。
- 場面を 2D の並びへ貼る所は 2D の draw call に数えない（`draw2d_calls` は 0）。

### 診断を付けた時の重さ（frame p50・ms。直す前と後を入れ替えながら 6 本ずつ = 部屋 24 区間・field 12 区間の中央）

| room | 0.49 | 1.01 | 0.50 | 0.52 | 1.04 |

  直しを入れた最後の engine で測り直すと、部屋は p50 の平均で 0.498 → 0.506 ms（+1.6%・24 区間ずつ。温まった後ろの 2 区間は 0.450 → 0.468・0.433 → 0.440）、

  1 回ずつの比べでは ±20% に見えるので、入れ替えながら何本か取って中央で読む。

### 置いた物を batch へ分ける所の直し（field 12,000・`SCENE=field COUNT=12000 REPEAT=2`）

JFR（2026-11-14 21:42・直す前）でメインスレッドの標本 908 のうち 204 が `Render3d.ScenePlan.sceneDrawsOf` の複製 1 つのインタプリタの frame、
56 が `Field.instancesAt` のインタプリタの frame だった。`-XX:+PrintCompilation` を付けた回（21:59・直す前）の行:

```
7850 21640 %     3       $pkg$github$ababup1192$flix_game_engine.Render3d.ScenePlan.Def$sceneDrawsOf$1063480::staticApply @ 71 (1242 bytes)   COMPILE SKIPPED: stack not empty at OSR entry point (retry at different tier)
7803 21605 %     3       Field.Def$instancesAt$1064993::staticApply @ 110 (261 bytes)   COMPILE SKIPPED: stack not empty at OSR entry point (retry at different tier)
7842 21637 %     4       Field.Def$instancesAt$1064993::staticApply @ 110 (261 bytes)   COMPILE SKIPPED: OSR starts with non-empty stack (retry at different tier)
```

大きさ（1,242 バイト）ではなく、1 コマに 1 回しか呼ばれない関数の中のループを途中から JIT（OSR）できない形だった。
`Render3d.Material.splitByMaterial` の `List.map` のラムダが `sceneDrawsOf` の中へ展開されていた。
ラムダの末尾は record で、呼び出しでは終わっていない。それでも OSR を諦めた理由は【不明】（ラムダの中身を def に出すと諦めが消える事だけ確かめた）。
ラムダの中身を `@DontInline` の `placedDrawOf`（末尾は record）へ出し、ベンチの `Field.instancesAt` も同じ形で `instanceAt` へ出した。
直した後の JFR（22:21）は標本 684 のうちインタプリタの frame が 35（直す前は 908 のうち 292）。

main（6855cdb2）と直した engine を 1 本ずつ交互に 2 本ずつ（2026-11-14 22:18〜22:24・1 本は 2 区間）。main の側のベンチにも `Field.instanceAt` の直しを当てたので、差は engine の直しの分。時間は ms。

| engine | frame p50（4 区間） | `cpu_phases` の `split` |
|---|---|---|
| main（6855cdb2） | 24.00・24.02・22.95・22.67 | 17.73〜18.16 |
| 直した後 | 18.78・18.93・18.49・18.55 | 14.57〜14.89 |

- 直した後も標本の 34% は record の欄の引き当て（先頭が `String.equals` か `RecordExtend.lookupField`）。呼び手の def で多いのは
  `Render3d.Batch.hasSameTree`（`MaterialFields` の `spec`・`emission`・`metallicRoughnessShade`）・`Render3d.Batch.kindBits`（`ProgramKind` の Bool の 6 欄）・
  `Render3d.Batch.batchOf`・`Render3d.Instancing.packDraw`（`MeshDraw` の `fields`・`world`・`tint`）。JIT の中のインライン展開で行がずれる事があり、欄までは確かめていない。直していない。

## 初めての 1 回（`make run FIRST=1|skin`・plans/engine-first-use-hitches.md）

測った日 2026-11-25 / Apple M4 Pro・macOS / WebGPU（PC は Dawn・ブラウザは Chrome 156 のヘッドレス）/ engine 0.112.0 / 起動し直して 3 回（「a / b / c」）。

### 物差しの注（PC とブラウザを並べる時）

- PC の frame は `frame#dt`（1 コマの間隔。更新・送る・swap の待ちを含む・この窓は 120 Hz に張り付く）。ブラウザの cpu は `fgeStats` の wasm の CPU だけ（rAF の待ちを含まない）で、間隔はいつも 16.7 ms の倍数。
  同じ物差しで並べるなら、3D の描き手の CPU（split・draw）どうしか、間隔どうし（ブラウザの frame_max）で比べる。
- 作り直しや初めての道は JVM ではその時に初めて通るコード（JIT の前）で、同じ仕事でも wasm より遅く出ることがある。

### 段 4 の後（ブラウザで glb の中の絵を画素を読まずに上げる・`first=glb`）

`make bench-web BENCH=scene3d ARGS='first=glb&keyed=<0|1>&n=300&shapes=137&mats=8&verts=600'`。120 コマ目に `assets/props_1f.glb`（retro3d-horror-starter の束・1.5 MB・
primitive 388・頂点 17,662・絵 46 枚 370 KB）を解き、その後のコマで描く。keyed=0 は今までの読み方（`fromGlbTexturedUsingOptions`）・keyed=1 は
`fromGlbTexturedKeyedUsingOptions`（形の鍵を key から・絵は届いた時に JS が解いた ImageBitmap のまま GPU へ）。3 回ずつ。

| | 解く仕事（work_max） | 区間の cpu max | 初めて描いたコマの split max | 同 draw max |
|---|---|---|---|---|
| keyed=0 | 229.6 / 230.7 / 231.5 | 353.1 / 355.6 / 356.3 | 37.2 / 37.4 / 38.3 | 84.2 / 84.7 / 85.3 |
| keyed=1 | 177.4 / 177.5 / 178.5 | 227.7 / 227.9 / 228.7 | 15.7 / 15.9 / 16.2 | 32.2 / 32.3 / 32.7 |

- 絵を wasm へ読み戻す往復（読み戻し・3 回の写し・SHA-256）と、絵 1 枚ごとの createImageBitmap の待ちが消え、解く仕事が 230 → 178 ms。
  初めて描くコマも、形の SHA-256 と絵の画素の上げが消えて split 37 → 16 ms・draw 84 → 32 ms。
- 残る 178 ms は glb の構文読み（JSON・accessor・形を組む）で、束が届いたコマの 4 分の 3 を超える（計画の 6 の「① Web Worker は 3 割を超えた時に相談」に当たる）。
- `web-capture --dev capture:150`（WebGPU と WebGL2）で keyed=0 と keyed=1 の絵はバイトまで同じ。

### glb の読み方の二乗とコピーを消した後（`first=glb&keyed=1`・つまみ `warm=1`・`glb=<名前>`）

`Gltf` の読み方から、番号で引くたびに JSON の配列を作り直していた所（`objectAt`）・`Vector.slice` が束全体を写していた所・1 成分ごとに `Float64.pow` で float を組んでいた所を消した。
`warm=1` は読み込みの時に `assets/entrance.glb`（テンプレートの起動の束への symlink・primitive 107）を 1 回解いてから測る（ゲームが起動の束を先に解いた後の、wasm のコードが温まった状態）。
`glb=<名前>` は解く束を `assets/<名前>` に替える。3 回ずつ・起動し直して。

| | 解く仕事（work_max） | 区間の cpu max |
|---|---|---|
| 前（fbb169854） | 174.5 / 174.0 / 173.5 | 225.6 / 224.1 / 223.9 |
| 後 | 97.4 / 94.6 / 96.0 | 147.3 / 147.0 / 148.1 |
| 後・`warm=1` | 67.4 / 65.5 / 67.3 | 121.3 / 118.1 / 121.8 |

- 解く仕事は 45% 減った。残りの差（ウォームアップ前と後の約 30 ms）は wasm のコードを初めて走らせる時の分。
- 区間の cpu max には、解いた形を同じコマで描く split（16〜19 ms）と draw（32〜34 ms）が乗る（ゲームでは集まりを 1 コマ 8 ms ずつ作り直す側が受け持つ）。
- `web-capture --dev capture:150`（WebGPU・WebGL2・keyed=0 と 1）で前と後の絵はバイトまで同じ。
