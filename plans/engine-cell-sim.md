## 1. サンプル（作った物）

`cinder_lab`（題名 Cinder Lab）: 古い溶鉱炉の下の暗い坑で、1 粒 = 1 画素の格子の中を掘り手が歩き、材料を置き、術（掘る・火・爆弾）を撃つ。
仕組みは同じジャンルから取ったが、題名・絵・色・名前・音・面は自前（材料は一般名）。

| 種類 | 材料（Doc の名前） | 規則（コード） |
|---|---|---|
| 粉 | sand・gravel・ash・gunpowder・bomb | 下へ落ち、斜めに崩れる（崩れやすさ `slide`）。自分より軽い液体の中は沈む（`density`） |
| 液体 | water・oil・lava・acid | 下・斜め下・横へ `dispersion` 升まで流れる。重さで層に分かれる（油は水に浮く・酸は水の下） |
| 気体 | smoke・steam・gas | 上へ昇り、寿命で消える。湯気は冷えると水に戻り、隣を温める。燃える気体は燃え尽きると小さく爆ぜ、溜まり全体が連鎖する |
| 固体 | stone・soil・wood・grass・ice・basalt・barrel・spring・vent | 動かない。熱を溜めて燃える（木・草・樽）か溶ける（氷 → 水）。泉と噴き口は水・溶岩を出し続ける |
| 火と熱 | fire | 燃料の隣で熱（`heatOut` × `absorb`）を配り、熱の限度（`heatLimit`）で燃え始める。燃え尽きると `burnInto`（灰・煙）。水に触れると消えて湯気 |
| 反応 | — | 溶岩 + 水 → 黒い石（basalt）+ 湯気。酸は 4 近傍の 1 つを溶かして強さを減らし、尽きると消える（`acidResist` で耐える）|
| 爆発 | gunpowder・bomb・barrel の `blast` と手の爆発 | 円を削る（石は芯の半分だけ削れる）・粒を外へ飛ばす（飛ぶ粒は燃える物なら火の付いたまま）・火花・縁に火・光と画面の揺れ |

場面（`make render-all` の gallery と、動画の 2 場面）:
- `main` 坑道（768 × 432・カメラは掘り手を追う・見える範囲の周りの区画だけ起こす）
- `showcase`・`burn` 見本の棚（4 つの鉢）
- `chain`・`chain2` 1 画面の連鎖の仕掛け（操作なしで 25 秒）。動画は `debug/video/chains.mp4`
- ブラウザ版 = 地形ガチャ（`src/gacha/`・`build/web-gacha`）: 30 秒ごとに種から洞窟と仕掛けを組み直し、タップで爆弾や材料を落とす

テスト 30 本（`test/TestCells.flix`・`TestStarts`・`TestPalette`・`TestDocs`）: 落ちる・崩れる・沈む・浮く・平らになる・溶岩と水・燃え尽きる・木が燃える・氷が溶ける・火薬が爆ぜる・酸が溶かして尽きる・気体が昇る・爆発・同じ種なら同じ格子・区画を飛ばしても同じ・窓の外は止まる。

## 2. 描く口（調べた結果: 足りている）

**毎コマの格子を 1 枚の絵として上げる口は engine に既にある**: `App.withSpriteAtlases(w -> List[AtlasUpload])`
（`{ texture, key, baked = { side, regions, pixels } }`）→ `Platform.GpuResources.ensureTexture(name, key, w, h, argb)`。

- key が前のコマと違う時だけ上げる。大きさが同じなら GPU の絵を作り直さず画素だけ差し替える（`RenderPaint.Internal.TextureTable.ensureTexture`）。
- 3 つの描き手: GL（`RenderTexture.updateTexturePixels`・glTexSubImage2D）・WebGPU（`WebGpuPaint.webGpuUploads#writeArgb` → `rewriteSlot`）・
  CPU の描き出し（`HeadlessRender.imagePngs` で PNG に落として `texturePath` で貼る）。cinder_lab は 3 つとも同じ絵になるのを確かめた（WebGPU と GL は `bin/gl-capture.sh` で実機の窓）。
- 空気の升は α = 0 で透かし、奥の遠景（`bg_cave_far.png`）は普通のスプライトで後ろに敷いた。

足りない所（engine に入れる時に直したい・どれも小さい）:
1. **正方形しか受けない**（`AtlasUpload#baked#side`）。428 × 240 の絵を 428 × 428 で上げている（帯域が 1.8 倍）。
   推す答え: `App.withDynamicTextures(w -> List[{ texture, key, width, height, pixels = Unit -> Vector[Int32] }])` を engine_world に足す（中は同じ `ensureTexture`。GpuResources の型は既に幅と高さを別に受ける）。
   **pixels は関数で受け、key が前と違う時だけ呼ぶ**: 今の `withSpriteAtlases` は毎コマ `(r#spriteAtlases)(world)` を呼ぶので、Flix が先に値を作り、key が同じでも塗りの代金を毎コマ払う（cinder_lab は塗った絵を World に持ち、塗った刻みだけを key に入れて逃げた）。
2. **`Vector[Int32]` で渡す**ので、格子の配列から毎コマ 1 回写す（428 × 240 なら 0.1 ms 程度で、今は問題にならない）。
3. 名前が「ドット絵のアトラス」で、毎コマ変わる絵に使うと読み違える（1 で解消）。
4. 描き出し（SoftRaster）は貼る絵を PNG の画素の大きさのまま出力の画素に置く（実機は design の px）。cinder_lab は描き出しだけ 2 倍の PNG を作って合わせた（`debug/tex2x`）。engine の `HeadlessRender` の不具合として直すのを推す。

- **計算する範囲を画面より広く（1,024 四方）**: カメラの近くだけ起こすと 1 割 2.3 ms・5 割 5.7 ms（PC）。重さの多くは「不変の World に見せるために毎刻み 1,024 四方を Vector ↔ Array で 2 回写す」代金（約 2 ms・JFR で確かめた）。
  engine に入れる時は区画ごとの Vector に割り、眠った区画は写さない形にする（8 章の決めごと 3）。
- 1,024 四方を全部起こすのは 1 本では無理（9 割で 45 ms・ブラウザは 150 ms）。並べると PC は 15 ms。
- 並べ方（区画を市松の 4 組に分け、組の中は同時に回す）は、組の中の区画どうしが互いの粒に届かないことで 1 本と同じ答えになる（前提は 4 章の不変の条件: 1 粒が 1 刻みに読み書きする距離 ≤ margin（6）< 区画の半分（32）・dispersion は丸める）。

JFR で効いた直し（同じ場面で 2〜3 倍）: Flix の別の関数への末尾呼び出しは trampoline の物を作るので、熱い所の Unit の関数の末尾に `; ()` を置いて末尾呼び出しを外した。乱数は 1 回の mix にした。

## 4. 決定性

- 乱数は順に引かず、(種・刻み・升・用途) の番号から作る（`CellKernel.roll`）。区画を飛ばしても乱数の並びがずれない。三角関数は使わない（術の向きは差を長さで割る・平方根は IEEE の丸めが決まっている）。
- 1 刻みの中の順: 手の編集 → 区画の組 0 → 3（組の中は下の行から上へ・行ごとに左右を交互）→ 飛ぶ粒 → 爆発（区画の番号の順）。
- 動いた粒には刻みの印（8 bit）を付け、同じ刻みで 2 度動かさない。
- 区画を飛ばしても同じ答え: 粒が変わった時に、その区画と縁から 6 升以内の隣の区画を「今の刻み」と「次の刻み」の両方で起こす（今の刻みにも起こすのは、後の組で回る区画が今入ってきた粒に反応するため）。
  確率で動かなかった粒（崩れそうで崩れなかった砂など）は起きたまま待つ。`testSkippingSleepingChunksGivesTheSameGrid` が全部回した時との一致を固定する。
- **成り立つ前提（不変の条件）: 1 粒が 1 刻みに読み書きする距離 ≤ margin（6）< 区画の一辺の半分（32）**。液体の `dispersion` は Doc の値なので、読む時に margin へ丸めて 1 行知らせる（docs/error-handling.md の既定値で続ける形）。7 以上だと区画を飛ばした時の答えがずれ、33 以上だと並べた時に同じ組の区画どうしが同じ升へ届く。並べる口は `unchecked_cast` で IO を隠しているので型では止まらない — API の文書とテスト（`dispersion = margin` ちょうど）で縛る。
  aux は 8 bit なので、Doc の `burnTicks`・`life` は 0..255 に丸めて知らせる（今は 256 以上を書くと黙って折り返す）。爆発は区画ごとに 1 刻み 8 個まで積み、9 個目からは捨てる（燃える気体の溜まりで起きる）— 上限と捨て方を API の文書に書く。
- 指紋の結果（JVM と wasm・CPU 1 倍と 4 倍）:

| 場面 | JVM 1 本 | JVM 4 本 | wasm CPU 1 倍 | wasm CPU 4 倍 |
|---|---|---|---|---|
| 画面 10 / 50 / 90 % | -2101769426 / 949389476 / -2086186216 | 同じ | 同じ | 同じ |
| 1,024 窓 10 / 50 / 90 % | 2000705187 / 1175382000 / -1315240969 | 同じ | 同じ | 同じ |
| 1,024 全部 10 / 50 / 90 % | 61686529 / -452587162 / 1665453953 | 同じ | 同じ | 同じ |
| 坑道に台本 600 刻み（今の規則） | -1995307195 | 同じ | 同じ | 同じ |

規則を足すたびに値は変わる（爆弾・樽・燃える気体の連鎖を足した後の坑道の値が最後の行）。比べはいつも同じ版の jar と wasm で取った。

## 5. ブラウザで並べる道（推す答え: (a)）

前の調べのとおり TeaVM の WasmGC はスレッドが擬似で共有メモリも無い。

| 道 | 中身 | 良い所 | 困る所 |
|---|---|---|---|
| (a) 区画を Worker ごとの wasm に | 画面を 2〜4 枚の帯に割り、帯ごとの Worker が同じ wasm で自分の帯の格子を持って回す。組（市松）ごとに: 縁の 6 升を両方向に渡す（隣の帯へ書いた升は持ち主へ書き戻す）・起こす印を OR で合わせる・爆発と動いた数を集める。爆発と飛ぶ粒は格子のどこにでも書くので、組の後の段は 1 か所（メイン）で回して結果の升を配る | 規則のコードが 1 本のまま（同じ Flix を同じ wasm で走らせる）。決定性はそのまま（組の順が同じなら答えが同じ） | 1 刻みに 4 回の待ち合わせ。縁の受け渡しの代金（428 × 242 なら帯の縁は数 KB）。glb の Worker の計画（engine-web-glb-worker.md）と同じ機種の handler の中に閉じる |
| (c) WebGPU の compute | 規則を WGSL に書き直す | 速い（1,024 四方を全部でも乗る見込み） | 規則が 2 本になる（Flix と WGSL）・JVM の描き出しとテストが同じ式を通らない・粒の移動の衝突（2 つの粒が同じ升へ）を GPU で決定的に解く工夫が要る（市松の 4 組の pass にすれば解ける）・WebGPU の無いブラウザで動かない |

**(a) を推す**: 規則を 1 本に保つことと、テスト・テープ・指紋が JVM でそのまま効くことを優先する。(c) は (a) で足りないと分かった時の次の手。
今の `Cells.Runner`（メインの配列をつかんだ closure を渡す形）は共有メモリの無い Worker では走らないので、**段 2・3 の API には Runner を出さない**。`Platform.Tasks`（1 つ預けて 1 つ受け取る）も N 個に分けて待ち合わせる口ではなく、寄せられない。
やる・やめるの線: 1 刻みに 4 回の待ち合わせ × postMessage の往復（実測が要る・数百 µs の見込み）を足しても、CPU 4 倍で 1 本より 1.5 倍以上速くならなければやめる。
試すのは計画の後（cinder_lab に Worker の比べを足してから）。

## 6. 剛体の物理とのつなぎ（今は入れない）

2D の剛体は v0.117.0 で engine_world に入った（`PhysicsWorld2d`・`App.addPhysics2d`・`Collider2d`・指紋は `StateHash`）。同じ作り（不変の World・region の中の配列）なので、つなぐ形は素直に書ける:
1. **粒 → 剛体**: 爆発や掘りで地形から切れた塊（固体の升のつながり）を見つけ、升の集まりを凸多角形（か小さな箱の束）にして `PhysicsWorld2d` へ入れ、格子からは消す。
2. **剛体 → 粒**: 剛体が眠ったら、覆う升を元の材料で格子へ書き戻し、剛体を消す。
3. 動いている剛体と粒: 剛体の形の升を「通れない」として格子の規則に見せ（液体を押しのける）、粒の重さを剛体へは返さない（片方向から始める）。
決めごと: 切れた塊の見つけ方（毎刻みでなく、爆発と掘りの後に、その周りの区画だけ）。
今入れない理由: 塊の見つけ方の重さが未測・粒の格子の側の API が決まっていない。指紋は engine の `StateHash` にそろえる（`Cells.fingerprint` を置き換える）。

## 7. engine に入れる時の形（層の物差しに照らして）

- 置き場は **engine_world**（ゲームの規則の側。機種に依らない純粋な Flix）。名前は 8 章の 10（推す: `PixelSim2d` を頭に、格子と 1 刻み・材料の表・塗りと光の格子の 3 つに分ける）。2D 専用なので `2d`。
- **抽象の層は置かない**: 実装は 1 本（Flix の規則）。並べる口（Runner）は段 4 まで API に出さない（5 章: 今の Runner は共有メモリの無い Worker で走らず、`Platform.Tasks` にも寄せられない）。
- 材料は **enum を engine に置かず、ゲームが番号と規則の組を登録する**形にするか（8 章の決めごと 1）。
- 描く口は 2 章の `App.withDynamicTextures` を足すだけ（RenderList・backend は触らない）。
- 塗りの側（名前は 8 章の 10）に置くのは仕組みだけ: 光の格子（前のコマの光を残して冷ます・光を通さない粒で弱める）・材料ごとの色とむら・液体と気体の透かしの欄。**暗い坑の地の色・奥の岩肌・石の塊・木目の模様は cinder_lab の画風なので engine に入れない**（固い物の模様はゲームが渡す関数・表にする。AGENTS.md の「画風はゲームごとに決め直す」）。Bloom は `App.withPostStack` で掛けられる（cinder_lab は Game・GachaApp で繋いだ）。

## 8. 決めごと（推す答え付き）

1. **材料をどこで決めるか**: (i) engine が固定の材料表（砂・水…）を持つ / (ii) ゲームが材料を登録し、engine は「粉・液体・気体・固体・火」の動き方と熱・燃える・酸・爆発の共通の規則だけを持つ。
   **推す: (ii)**。ただし名指しは少なくない: kernel が名指しする材料は 10（水・溶岩・酸・煙・湯気・燃える気体・火・玄武岩・泉・噴き口）、爆発に耐える「固い物」（石・玄武岩・泉・噴き口）と砕けた時の砂利、塗りが番号で引く模様（1・2・3・4・5・18）。(ii) にするには、欄（火の生成物・溶岩と水の生成物・固さ・砕けた時の材料）と役（湧き口・燃える気体）に直す。材料の id は AGENTS.md 4 節に従い外から作らせない型にする（`pub type alias` + 非 pub の enum）。この作業で段 2 は 6〜8 時間になる（9 章）。
2. **格子の 1 粒の形**: Int32 に bit で詰める（材料 8・aux 8・刻みの印 8・色のむら 7・燃えている 1）。**推す: このまま**。温度を 8 bit の aux と燃えている bit で兼ねる割り切りは、材料ごとに aux の意味（熱・寿命・強さ）を決める表で書く。
3. **不変の World に見せる形**: (i) 毎刻み全体を写す（今）/ (ii) 区画ごとの Vector に割り、起きた区画だけ写す。**推す: (ii)**。1,024 四方で約 2 ms の写しが消え、画面より広い世界が安くなる。
4. **刻みの印の 8 bit の折り返し**（印が今の刻み & 255 と同じ升はその刻みに回さない。新しく作った升は印が 0・熱を足すだけの書き込みは印が古いままなので、`tick % 256` が当たる刻みには、止まっていた粒だけでなく燃えている升の減りや気体の寿命も 1 刻み止まる）: **推す: 受け入れる**（答えは毎回同じで、動きが 1 刻み遅れるだけ）。気になれば印の bit を増やす（区画ごとの「最後に回した刻み」では、起きたまま 256 刻み動かない粒の誤りは解けない）。
5. **区画の大きさ**: 64。**推す: 64 のまま**（32 だと旗の代金が増え、128 だと眠れる所が減る・並べる時の組の中の区画が少なくなる）。
6. **描く口**: `App.withDynamicTextures` を足す（2 章）。**推す: 足す**（engine の拡張なので相談）。
7. **並べる口**: PC は JVM のスレッド（`Executors`）・ブラウザは 5 章の (a)。**推す: フェーズ 3 まで 1 本**（画面の大きさなら PC は 1 本で足りる）。
8. **塗りをどこでするか**: (i) CPU で 1 画素ずつ（今・3 つの描き手で同じ絵）/ (ii) 格子の Int32 をそのまま GPU へ上げ、色と光は ShaderDoc の面で塗る。**推す: (i) のまま、塗りを 2 段に分ける**: 地の色（材料・むら・模様。区画ごとに持っておけ、眠った区画は塗り直さない）と、光を掛ける段（光の格子は毎刻みにじんで冷めるので毎回全部の画素）。後の段は 1 画素あたり掛け算 3 つと足し算なので、今の塗りの 3 割程度の見込み（未測）。(ii) は WebGPU と GL と SoftRaster の 3 つに同じ式が要り、光の格子（前のコマを残す）を面で持つ口が engine に無い。

9. **セーブと巻き戻し**: 持つ物は cells（刻みの印も答えに効くので Int32 を丸ごと）・flyers・tick・seed（材料は名前の表で持つ — docs/save-compat.md の「id で持つ」）。区画を飛ばしても答えが同じなので、awake は保存せず読み込み時に全部起こしてよい。窓（カメラ）の並びも答えに効くので、テープと F8 の再現の条件に入れる。
10. **名前**: engine_world に `Grid.Cell`（マスの座標）と `Material`（DualGrid の地形の材料）が既にあり、`CellGrid2d`・`CellMaterial2d` の Cell と Material は別の意味になる。候補は `SandGrid2d`／`PixelSim2d`／`FallingSand2d`（業界の語は falling sand・pixel simulation）。**推す: `PixelSim2d`**（相談の時に決める）。
11. **Doc の形**: (ii) では材料の顔ぶれがゲームごとに違うので、スキーマは「名前 → 性質」の汎用の catalog にし、範囲（0..255・dispersion ≤ margin）をスキーマに書く。名前の打ち間違い（`heatInto: "stem"`）は今は黙って空気になるので、読む時に 1 行知らせる。
