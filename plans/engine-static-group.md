# 動かない物の束（StaticGroup3d）— 案（相談用・未着手）

## なぜ

今の描き手は、毎コマ、場面の置いた物（`Scene3dCmd#instances`）を 1 つずつ全部見直す（`Render3d.ScenePlan.sceneDrawsOf`）:
視錐台の判定 → 材質ごとの分け（プログラムの引き当て）→ batch → 描く順 → instance の行の上げ直し。影の地図と奥行きの Pass でも同じ事をする。
だから 1 コマの時間が物の数に比例する。3D の箱庭（lamplighter）では 857 個で 14.1 ms・約 250 個で 5.7 ms（M4 Pro）だった。

町・森・ダンジョンは、物のほとんどが動かない。動かない物の準備を 1 回で済ませれば、毎コマの時間は「動く物の数」で決まる。
Unity の Static Batching・Unreal の Static Mesh・Godot の static な MeshInstance に当たる。

`plans/engine-scene3d-cpu.md`（1 個あたりを安くする）の結果を見てから着手する。そちらで十分に下がれば、この案の優先度は下がる。

## ゲームから見た形

```flix
// 読み込みの時に 1 回作る（純粋。中身の鍵は Lazy）。名前 = F8 と知らせに出る名前。
let town = Scene3d.staticGroup("town", items)          // items: List[(String, Instance3d)] — 鍵つきの置いた物

// 毎コマ、場面に載せる。束ごとに掛ける値だけは毎コマ替えられる。
{ groups = (town |> Scene3d.withGroupTint(skyTint)
                 |> Scene3d.withGroupLightmapIntensity(skyLevel)
                 |> Scene3d.withoutItems(Set#{"House_o5"})) :: Nil      // この鍵の物は束から外す（描かない）
  | Scene3d.scene(camera, size) }
```

- **束の中の物は、置き場所・形・材質が変わらない**。変えたい物（箱庭の「低く縮めている家」）は `withoutItems` で外し、ゲームが普通の `instances` に置く。
- **毎コマ替えられるのは束ごとの値だけ**: tint・lightmap の intensity・emission の倍率。物ごとに違う値にしたければ、束を分ける（箱庭なら「早く点く窓」「遅く点く窓」）。
- 骨つきの物（Pose）・半透明の物は束に入れられない（作る時に外して知らせを 1 行）。半透明は描く順が目からの距離で毎コマ変わるため。
- `Scene3dCmd` に欄 `groups` が増える。`Scene3d.scene` の既定は空なので、今のゲームは書き換え不要（`{ .. | Scene3d.scene(..) }` の形で書いていれば）。

## 中でする事

1. **作る時（1 回）**: 物ごとの world の境界・束全体の境界・材質ごとの分け・batch と描く順を決めて持つ。
2. **GL**: 最初に描く時に、instance の行（world の行列など）を束ごとのテクスチャへ 1 回だけ上げる。毎コマは
   「束全体が視錐台の外なら飛ばす → 中なら、升目（下の 4）で見える物の番号だけ選ぶ → batch ごとに draw」。プログラムの引き当ては束につき 1 回。
3. **影の地図・奥行きの Pass**: 同じ束を同じ準備で描く（別々に組み直さない）。
4. **升目で絞る**: 束の中の物を粗い升目（世界を上から見た 2D の升目で足りる）に入れておき、視錐台に掛かる升目の物だけを見る。
   最初の版では省いてよい（束全体の判定 + 物ごとの判定を作り置いた境界でするだけでも、境界の作り直しと材質の引き当てが消える）。
5. **CPU の描き手（SoftRaster3d）**: 束を「同じ値を掛けた置いた物の並び」へ開いて、今の道で描く。絵は「束の中身を instances に置いた時」と同じ（`gl-parity` はこの形で比べる）。

## 決まりと門

- 絵は「束を使わずに同じ物を instances に置いた時」と 1 bit も違わない（GL・CPU とも）。`bench/gl_parity` に、束を使う場面と使わない場面の対を足す。
- 束の中身が変わったら別の束（中身の鍵が変わる）。古い束の GL の資源は、今の mesh の退避（eviction）と同じ世代の仕組みで片づける。
- 診断（`FrameDiagnostics#scene3dCounts`）に、束の数・束から描いた物の数・毎コマ見た物の数を足す。

## 見積もり（直近の実績から・実時間）

- 下位モデルの作業と私の検証で、4〜6 時間。GL と CPU の両方・影と奥行き・`gl-parity` の門まで含む。
- リスク: GL の instance の行の持ち方（今は毎コマ 1 枚のテクスチャへ全部書く）を、束ごとの持ち越しと両立させる所。ここで詰まったら、
  2 の「1 回だけ上げる」を諦めて「準備（境界・材質・batch）だけ作り置く」へ下げる（効果は半分ほどの見込み）。

## 効果の見込み

- lamplighter の今（約 250 個のうち動かない物が約 200）: 5.7 ms → 3〜4 ms の見込み（測っていない）。
- つなぐ前の 857 個: 14.1 ms → 上と同じ程度になるはず（毎コマ見るのは人と動物と縮めている家だけ）。
- 物を何千個置く場面: 今は置けない。束なら、見える升目の分だけになる。

## 人に決めてほしい事

1. ゲームが「動かない」と明示する形（上の `staticGroup`）でよいか。明示しない案（同じ値を渡したら勝手に使い回す）は、ゲームが毎コマ値を作り直すと効かない。
2. 束の中の 1 個を変える時は「束から外して、普通の物として置く」でよいか。
3. `engine-scene3d-cpu.md` の結果を見てから着手、でよいか。
