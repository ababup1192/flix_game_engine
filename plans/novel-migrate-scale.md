# ノベルの移行の比べと退行の確かめを、長い物語・多い分岐でも速く保つ（設計）

- 日付: 2026-11-16
- 状態: **設計（レビュー 1 回目 72 点 → 2 回目 88 点で GO・残りの 1 件を直した 3 版）**。試作の測りは済み。engine に手を入れる段（J・E2・F・I2・G）は作る前に人へ相談する。
- 親: [novel-tape-deck.md](novel-tape-deck.md)（テープとデッキの下書き）・[docs/migrate-diff.md](../docs/migrate-diff.md)・[docs/render-cache.md](../docs/render-cache.md)・[docs/flow.md](../docs/flow.md)
- 人の依頼: 「今後もっと長いストーリーや分岐が増えるので、根本から速くしたい」

## 0. 結論

1. **「.flix を直すと全部のコマが冷える」は誤りだった**。コマの鍵は前から「描く命令のハッシュ + エンジンの fpkg + JVM と OS」で、
   jar の指紋（`programDigest`）は効果音の WAV の鍵にしか入っていない。ゲームの .flix を直して jar を作り直しても 226 枚が全部写った（M4）。
   全部を冷やしていたのは **JVM の起動旗**（`migrate shoot` が本数ごとに変える `-XX:MaxRAMPercentage`・`-Xlog` など）。これは直した（コミット 538c63f5・段 A）。
2. 鍵の一致で省けるのは「**時刻のずれない直し**」だけ。world の層には flow の頭からの時刻で動く揺れが入っていて、**頭で 1 フレームずらすと、その後ろの比べのコマ 187 枚の鍵が全部変わる**（M10）。
   待ち・字の速さ・演出の秒を触る直しでは、ずれた所から後ろを全部塗り直す。だから **塗り自体の速さ（J）** が、鍵で省く手（C・D）と同じくらい要る。
3. 塗りの時間の半分は背景のぼかし（`ShaderEval.blurTex`/`blurSum`）、全体の 42% は Flix のレコードの欄を引く所（`RecordExtend.lookupField`）（M11）。1 枚 4〜6 コア秒。
4. 塗りは鍵を作る時間の **約 650〜850 倍**（1 コマ 0.46〜0.59 秒 対 0.7 ミリ秒）。13 本の全コマの **63% は前に流した別の flow のどこかのコマと鍵が同じ**、比べのコマ 2,058 枚のうち鍵の種類は 836（41%）。
5. JVM 1 本の 9.8〜10.9 GB は **ほぼゴミ**。Full GC の後に生きている物は 0.2 GB 前後。`-Xmx2g` で RSS 2.45 GB・遅くならない（M5）。
6. 順番: **A 鍵の旗（済）→ B ヒープと置き場の上限 → C 鍵で比べる・比べた結果を覚える（diff）→ D 鍵を先に・塗りは差のあるコマだけ（I1 同じ鍵は 1 回だけ塗る を含む）→ J 塗りを速く → E1 常駐で流す → F 前置きを 1 回だけ流す → G ノード単位（今は作らない）**。
   A〜D と E1 は engine を変えない（Go とテンプレートだけ）。J・E2・F・G は engine に手を入れるので相談する。

## 1. 目標

物語の長さ 5 倍・分岐 3 倍（flow 13 本 → 約 40 本・1 本 6,600 コマ → 約 33,000 コマ・比べのコマ 2,058 → 約 31,000 枚）を想定する。

| 場面 | 今（血鱗・13 本）【推】 | 目標（5 倍 × 3 倍） |
|---|---|---|
| ① 何も変えずにもう 1 回 | 約 65〜75 秒 | **2 分以内** |
| ② ゲームの .flix を 1 か所直した・時刻はずれない（描く物の変わったコマ 200 枚以下） | 約 2〜2.5 分（塗り 200 × 5 コア秒 / 12 ≒ 85 秒が足される） | **3 分以内** |
| ③ 待ちや演出の秒を 1 か所直した（その後ろの比べのコマが全部変わる。1 本の半ば・その flow を通る 1/3 の flow で 5,000 枚） | 約 4〜6 分 | **10 分以内** |
| ④ engine を直した後（全部の鍵が変わる・冷えた状態） | 冷えた時 978 秒（3 本ずつ） | **30 分以内**（J の後に測り直して決め直す） |
| メモリ | 1 本 8 GB の見積もりで本数を絞る | 1 本 3 GB 以下・本数は CPU だけで決まる |

「人の目で見る迷った差の頁」の作りと線引き（docs/migrate-diff.md の合格線）は変えない。速くする所は撮る・比べる道だけ。

## 3. 案と効き目

### A. 鍵の JVM の起動旗を絵に効く物だけに（**済**・538c63f5）

- `RenderCache.runtimeId` の「起動旗の全部」を、`RenderCache.paintFlagsOf`（`-Dsun.java2d.*`・`-Dawt.*`・`-Djava.awt.*`・`-Dswing.*`・`-Dsun.font.*` だけ残す）に替えた。
- 効き目: `--jobs` を変える・`-Xmx` を足す・GC の記録を取るだけで、全部のコマを塗り直していたのが無くなる。B の前提。
- novel-tape-deck.md 1 章の「写しの作業場では 1 回 jar が作り直された（理由は未確認）→ 冷えた」は、jar ではなく旗が変わったためと読める【推】。

### B. JVM のヒープと render-cache の置き場に上限を決める（Go だけ）

- `shoot` は今 `-XX:MaxRAMPercentage=60/本数` を渡し、本数を「メモリ 8 GB に 1 本」で絞る。これを **`-Xmx3g`（1 本の上限）** にし、本数は CPU だけで決める。
  3g の根拠: 若い世代の GC の後の最大 1.8 GB（M5）に、長さ 5 倍で World の列が増える分の余裕を足した物（Full GC の後の 0.2 GB のうち World の列はさらに小さいので、5 倍でも数百 MB【推】）。
- **render-cache の置き場の上限**: `bin/fge render-cache prune` の既定は 4,096 MB で、reference-check と compare のたびに古い順に消す。比べのコマの PNG は 1 枚約 0.86 MB（M8 の置き場で 904 枚 781 MB）なので、
  5 倍 × 3 倍の鍵の種類（約 12,700 枚）だけで約 11 GB になり、**消されて毎回冷えた状態から始まる**。
  `shoot` は撮る前に「基準の記録のコマの数 × 0.9 MB × 2（前と後）」を見積もり、`FGE_RENDER_CACHE_MAX_MB`（新しい環境変数・Go の prune が読む）がそれより小さければ 1 行で知らせる。既定の上限は 16 GB に上げる（置き場はクローンでなく普通のファイルなので、ディスクの空きも見て知らせる）。
- 効き目: メモリ 1 本 10 GB → 2.5〜3.5 GB。消えて冷える事故が無くなる。
- 見積もり: 1〜2 時間（`shoot.go` の旗・`autoJobs`・prune の上限・テスト・docs の 2 か所）。

### C. 鍵が同じコマは画素を比べない・比べた結果を覚える（Go の `diff` だけ）

- `shootFrames` は既に `frames/<層>/drawhash.txt`（コマの番号 → 鍵）を書いている（VideoOut）。`diff` はこれを読み、tape.json の `frames[].file`（`f0126.png`）の番号で鍵を引く。
- 前と後の鍵が同じなら「同じ」として画素を読まない（鍵が同じなら PNG は 1 バイトも違わない、が DrawHash の約束）。違えば今の画素の比べ。drawhash.txt が無い記録は今まで通り。
- **鍵が `-`（鍵を作れなかった・キャッシュを使わない・鍵だけの回の pass のコマ）どうしは「同じ」にしない**。片方でも `-` なら画素で比べる。
- **画素を読まない時も、PNG があるかは確かめる**（「撮れていない記録」で止める今の判定を残す。D で PNG を書かないコマは、鍵がある事を「撮れた」と見る）。
- 鍵が基準と違うのに new の記録に PNG が無いコマは「撮れていない」で止める（D の I1 で写し忘れた時に、比べずに通さない）。
- 合格線との関係: 鍵が同じ = 画素が同じなので、lineDone・mid・backdrop3d・時刻のずれたコマのどの線でも差 0 として通る（今の比べでも同じ結果）。mid の `seconds` の比べ・音・出来事・承認は鍵と関係なく今のまま。
- 鍵にはエンジンの fpkg と JVM が入るので、**前の版（古い engine）と新しい版の比べでは鍵は一致しない** → 自動で今の画素の比べに戻る。効くのは「新しい版どうしの退行の確かめ」と、同じ engine どうしの移行。
- **比べた結果を覚える**（`<new の親>/diff-cache.json`）。鍵 = (前の PNG の SHA-256 か鍵, 後の鍵, 線の種類（lineDone・mid・backdrop3d）, 時刻のずれ（半フレームを超えるか）, 重ねた後の線引きの値の指紋, Go の比べの版の字)。
  覚えるのは数（差の画素の割合・平均・99% 点）だけ。線を超えた結果を覚えから出した時も、heat/*.png（毎回消す）は作り直す。
  前と後の engine が違う比べでも、直した後に描く物が変わらなかったコマは画素を読み直さない。
- 古いセーブの読み戻し（restore.json の frames）も同じ形で比べる【未確認: restore の frames の隣に drawhash.txt が書かれるか。無ければ覚える方だけ効く】。
- 効き目: 退行の確かめの diff 14.5 秒 → 1〜2 秒（13 本）・5 倍 × 3 倍で 220 秒 → 10〜20 秒【推】。③ では時刻のずれた後ろは画素の比べのまま。
- 見積もり: 3〜5 時間（読み・覚える場所・テスト 8〜10 本・docs/migrate-diff.md）。

### D. 鍵を先に作り、塗る・写すのは差のあるコマだけ（テンプレートと Go）

- 今の `shoot` は比べのコマを全部 PNG で書く（冷えていれば塗る・当たれば写す 1 枚 8 ミリ秒前後）。記録 1 つが 2.3 GB。
- 段 1: flow を流し、比べのコマは **鍵だけ**を書く（テンプレートの `shootFrames` が `MIGRATE_PAINT=keys` の時だけ paint を `Nothing` にする。今の WhyNot（paint を受け継ぐと比べのコマも塗られない）を、わざと使う形）。
- 段 2: Go が基準の鍵と突き合わせ、鍵の違うコマ・基準に無いコマの番号だけを `FGE_VIDEO_PAINT=frames:A-B,…` で渡してその flow を流し直す（差のある flow だけ）。
  - **I1（同じ鍵は 1 回だけ塗る）もここで**: 段 1 で全部の flow の鍵が集まるので、Go が鍵ごとに塗る (flow, コマ) を 1 つだけ選んで配る。並べた JVM が同じ鍵を同時に塗る事が無くなる（engine の RenderCache は変えない）。
  - 段 2 の後に Go が、塗った flow の PNG を、同じ鍵を持つほかの flow の new の記録のコマへ写す（APFS なら clone）。これで「基準と鍵が違うコマは new の記録に必ず PNG がある」が成り立つ（テスト: 2 本の flow が同じ鍵を持ち、1 本だけで塗った時、もう 1 本にも PNG があり diff が画素で比べる）。
- **基準の記録は必ず全部の PNG を持つ**。退行の確かめでは基準は前の回の new の記録になるので、`migrate accept`（新しい記録を基準に上げる時）か `shoot --full` で欠けた PNG を埋めてから基準にする
  （render-cache から写す。消えていれば塗る）。頁と承認の `images` は基準と new の記録の中の PNG だけを指す（render-cache の置き場は指さない — prune で消える）。
  new の記録の PNG が無いコマは鍵が基準と同じコマなので、頁では基準の PNG を左右に並べる。
- ゲームに写したテンプレートが古い FlowVideo（`MIGRATE_PAINT` を読まない）の時は、段 1 で PNG が書かれる。Go は段 1 の後に `frames/world/` に PNG があれば段 2 を飛ばす（今と同じ結果・速くならないだけ）。
  血鱗のゲームの FlowVideo をテンプレートに合わせる段を別に置く（下の段取りの D2）。
- 前の版との比べ（鍵が一致しない）では段 2 が全部のコマになり、今と同じ。
- 代わりの案（比べた）: render-cache から APFS の clonefile で写す（`RenderCache.copyFile` を `Files.copy` から clone に替える）。2 回流さずに、写す時間と置き場がほぼ 0 になる。
  ただし engine_tools を変える・APFS 以外では効かない・I1 の効き目（同じ鍵を重ねて塗らない）は得られない。**D を先に、clone は D の後に足りなければ**。
- 効き目: ①② では PNG のコピーと置き場がほぼ 0（5 倍 × 3 倍で 1 本 6 秒 × 40 本 / 4 本 ≒ 60 秒が消える）。差の出た flow だけ 2 回流す（1 本 5〜10 秒）。④ では I1 で塗るのが鍵の種類だけになる（13 本で 2,058 → 836 枚）。
- engine の変更: なし（`VideoOut.PaintRange.Frames` は既にある）。
- 見積もり: 5〜7 時間（テンプレートの分かれ道・Go の 2 段と配り・基準を埋める口・テスト）＋ D2 血鱗の FlowVideo を合わせる 1〜2 時間。

### J. 塗りを速くする（engine: ShaderEval の中・口は変えない）

- M11 の通り、塗りの半分は背景のぼかし、全体の 42% はレコードの欄を引く所。
- `ShaderEval.blurSum`（src/engine/shader/ShaderEval.flix）を読んだ: 画素ごと・**色の欄ごと**に呼ばれ、点（taps）ごとに `Num.sqrt`・`Num.cos`・`Num.sin` を計算し直し、
  `BlurTex` のレコードの欄を 5 つ引いて `sampleTexAs` を呼ぶ。点の位置（角度 i × 黄金角・距離 √((i+0.5)/taps)）は画素に依らないのに、毎回作っている。
- 手（どれも足し算の順と値を変えないので、PNG は 1 バイトも変わらない見込み）:
  (1) 点ごとの (cos(a)·r, sin(a)·r) を taps ごとに 1 回だけ表にする（同じ式で作るので同じ double になる）。
  (2) `BlurTex` の欄を繰り返しの外で 1 回だけ取り出す。(3) 色の欄ごとに読み直さず、1 回の点の巡りで全部の欄を足す（足す順は欄ごとに今と同じ）。
- 採らない手: ぼかした背景を 1 回作って使い回す — 背景は毎コマ動く（寄り・揺れ）ので、「ぼかしてから読む」と「読みながらぼかす」は画素が一致しない。GPU の道（sg_blur）とも食い違う。
- **塗った PNG は 1 バイトも変えない**のを門にする（`FGE_RENDER_CACHE=verify` で全部のコマを塗って突き合わせる・テンプレートの reference の SHA256SUMS）。
- 効き目: ぼかしの部分が 3〜5 倍【推】→ 塗り全体で 1.5〜2 倍（4〜6 → 2.5〜3.5 コア秒）。残りのレコードの欄を引く所（3D・面の塗り）まで手を入れれば、さらに【推: 測るまで分からない】。③ の 35 分 → 約 20 分、④ の 90 分 → 約 50 分。
- 見積もり: (1)〜(3) 3〜5 時間・ほかの内側の繰り返し 6〜10 時間（どちらも測りと verify の門込み）。**engine の ShaderEval（src/engine/shader）を変える（相談）**。

### E. 1 本の常駐の JVM で flow を続けて流す

- E1（Go とテンプレート・engine は変えない）: 今は flow ごと・セーブごとに JVM を起こす（13 + 12 回 → 5 倍 × 3 倍で 40 + 36 回）。1 回あたり起動 1.5 秒 + 字と Doc の用意 + JIT が温まるまで。
  `App.Headless` の常駐（`bin/fge resident`・テンプレートの `FlowVideo.jobs`）は既にあるので、`shoot` を「本数ぶんの常駐に flow とセーブを配る」形にする。
  効き目: 76 回 × 3〜4 秒 / 4 本 ≒ 60〜75 秒。見積もり 2〜4 時間。
- E2（engine_world・後回し）: `Flow.play` は全フレームの World を `outcome#frames` に持って返す。M5 で生きている物は 0.2 GB なので、5 倍でも B の上限に収まる見込み【推】。
  足りなくなった時だけ、`Flow.play` に「1 フレームずつ関数を呼ぶ形」の口を足す。mid のコマは命令が終わるまで撮る位置が決まらないので、その形でも撮る候補の World をしばらく持っておく所は要る。**engine_world の Flow に口を足す（相談）**。

### F. 共通の前置きを 1 回だけ流して分ける（engine: Flow に口）

- 13 本のうち 7 本（route_* 4 本・tape_* 3 本）は、直に、または `route_to_bones.flow` を通して `run route_to_fork.flow` で始まる。うち 5 本はさらに `route_to_bones.flow` まで同じ。
- Flix の World は書き換わらない値なので、常駐の中で前置きを 1 回流し、その終わりの World をそのまま各 flow の続きの始まりに渡せる（セーブに書いて読み戻さなくてよい）。
  `Flow.play` は既に `start = { world, state }` を受け取る。足りないのは「手順の列を前置きと続きに分ける」「続きの記録（フレームの番号・時刻・mark）を前置きの後ろへ繋ぐ」口。
- 確かめ方: テスト（テンプレートの 2 本で、分けた記録の drawhash.txt と tape.json が頭から流した物と 1 バイトも違わない）と、`shoot --verify-split`（時々・人が engine を上げた時に流す）。毎回は確かめない（毎回確かめると頭から流す事になり、効き目が消える）。
  手の状態（押したまま・`awaiting`）が空でない切れ目では分けない【未確認: `run` の切れ目で必ず空か】。
- 効き目は小さい: `MigrateOnly` では flow の計算は 1 本 1〜2 秒なので、今は 1 本 1 秒未満。5 倍 × 3 倍で 1 本 3〜5 秒・40 本で 30〜50 秒 / 本数。
- 見積もり: 6〜10 時間。**engine_world の Flow に口を足す（相談）**。J・E1 の後に、まだ足りない時だけ。

### G. ノード（ビート）単位で流して覚える（今は作らない）

- 単位 = 「ノードに入る時の World（の指紋）+ 流す入力」から「次のノードに入るまで」。単位ごとに記録を覚え、同じ単位は流さずに記録を繋ぐ。M7 の通り、13 本で単位の種類は 56・重なりは 55〜80%。
- 作らない理由:
  1. 揺れが flow の頭からの時刻で動くので（M10）、入る時刻の違う単位は描く物が違う。World の指紋に時刻まで入れると、同じ単位はほぼ前置きの共有（F）と同じ所にしか出ない。
  2. コードを直すと、どの単位の振る舞いが変わったかは流さないと分からない。**.flix を直した直後（いちばん多い場面）には効かない**。効くのは台本（.yarn）と Doc だけを直した時。
  3. 入力: flow の手はノードをまたいで書かれる（`drive viewer until choice`）。単位に切ると、手順の側も単位ごとに切り直す必要がある。
  4. 塗りは既に鍵で 1 回にまとまっている（M8）。G で減るのは流す時間（今 1 本 1〜2 秒）だけ。
- 作り始める合図: 台本と Doc だけの直しを数秒で確かめたくなった時。その時は「揺れの時刻をノードに入った時からにする」をゲームの見た目の判断として人に聞いてから。
- 見積もり: 15〜25 時間（World の指紋・単位の記録・手順の切り方・門）。**engine_world（相談）**。

### H. 塗りを GPU（Dawn の画面なし）にする案（門には使わない）

- 速さは一番出る（全コマの動画は 6,583 コマを GPU で 55 秒）。しかし **GL・GPU の絵は鍵の約束の外**（VideoOut の冒頭・docs/design/render-speed.md 3.5 節）で、機械・ドライバで画素が変わる。
  前の版（SoftRaster で撮った基準）と比べると、全部のコマに GPU と SoftRaster の差が出る。前と後の両方を同じ機械の GPU で撮り直すなら比べは成り立つが、基準も撮り直しになり（novel-tape-deck.md 3 章の保存した jar が要る）、門が機械に依る。
- 判断: デッキ（差の所をその場で塗って並べる）と人が見る動画に使う。冷えた時の速さは J と I1 で取る。

## 6. テープとデッキ（novel-tape-deck.md）との関係

- デッキ（差の所をその場で塗って並べる）は、**C・D の「鍵の違うコマの一覧」をそのまま頭出しの一覧に使える**。録画が要らないのは D と同じ考え方。
- デッキの「しおり」（beat の頭のセーブ）は、F の「前置きの終わりの World を受け渡す」と同じ物。F を作れば、デッキのしおりは常駐の中でその World をそのまま持てる。
  ただし M10 の通り、揺れが flow の頭からの時刻で動くので、しおりからの再生は「その flow の頭からの時刻」まで戻した World でないと同じ絵にならない（セーブに時刻が入るか【未確認】）。
- テープの ② の「前の版の jar を保存」は、前の版を撮り直す時（基準を撮り直すのは engine を直した時だけ）に要る。この設計の A〜F とは独立に進められる。

## 7. 危険と逃げ道

| 危険 | 逃げ道 |
|---|---|
| A で絵に効く起動旗を落とす（`-D` 以外で塗りを変える旗がある） | 残す側を名指しにしたので、知らない `-D` の入れ物は落ちる。疑いがある時は `FGE_RENDER_CACHE=verify` で毎回塗って突き合わせる（既にある）。Java の浮動小数は 17 から厳密なので `-XX` の旗で結果は変わらない |
| C で鍵が同じなのに画素が違う（鍵の取りこぼし） | DrawHash の約束が破れている事なので、`verify` で見つけて DrawHash を直す。C は `--no-keys` で今の画素の比べに戻せるようにする |
| C の覚えた結果が古い線引きのまま使われる | 鍵に線の種類・時刻のずれ・線引きの値の指紋・Go の比べの版を入れる。迷ったら `diff-cache.json` を消せば今と同じ |
| D で差のあるコマを流し直す時に、1 回目と違う所へ来る（決定性の破れ） | 2 回目の鍵が 1 回目と違えば止める（門の誤り）。`make determinism` と同じ考え方 |
| D で基準の PNG が欠ける（`--overwrite`・基準の消去・prune） | 基準は必ず全部の PNG を持つ（accept か `--full` で埋める）。頁と承認は記録の中の PNG だけを指す |
| B の `-Xmx3g` が 5 倍の長さで足りない | OOM で止まる（静かに壊れない）。`HEADLESS_JAVA_OPTS` で上書き（自分で渡した旗が勝つのは今と同じ）か E2 |
| B の置き場の上限が足りず prune で消える | 撮る前に見積もって知らせる。消えても塗り直すだけで間違わない |
| J で塗った絵が 1 バイトでも変わる | verify と SHA256SUMS で止める。変わった版は入れない（鍵の fpkg の指紋は変わるので、キャッシュの取り違えは起きない） |
| F で分けた記録が頭からの物と違う | テストと `--verify-split` で見つけたら、その切れ目では分けない（遅くなるだけで、間違わない） |
| 全体: 速くするための道が、比べの判定を変える | 段ごとに、前の判定と同じ（止める違い 0・迷った差の組が同じ・比べたコマの数が同じ）を門にする（novel-tape-deck.md 1.1 と同じ門） |
