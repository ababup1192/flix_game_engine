# ノベルの移行の比べと退行の確かめを、長い物語・多い分岐でも速く保つ（設計）

- 日付: 2026-11-16
- 状態: **設計（レビュー前）**。試作の測りは済み。engine に手を入れる段（E・F・G）は作る前に人へ相談する。
- 親: [novel-tape-deck.md](novel-tape-deck.md)（テープとデッキの下書き）・[docs/migrate-diff.md](../docs/migrate-diff.md)・[docs/render-cache.md](../docs/render-cache.md)・[docs/flow.md](../docs/flow.md)
- 人の依頼: 「今後もっと長いストーリーや分岐が増えるので、根本から速くしたい」

## 0. 結論

1. **「.flix を直すと全部のコマが冷える」は誤りだった**。コマの鍵は前から「描く命令のハッシュ + エンジンの fpkg + JVM と OS」で、
   jar の指紋（`programDigest`）は効果音の WAV の鍵にしか入っていない。ゲームの .flix を直して jar を作り直しても 226 枚が全部写った（2 章の M4）。
   本当に全部を冷やしていたのは **JVM の起動旗**（`migrate shoot` が本数ごとに変える `-XX:MaxRAMPercentage`・`-Xlog` など）。これは直した（コミット 538c63f5・段 A）。
2. 塗る時間は鍵を作る時間の **約 850 倍**（1 コマ 0.46〜0.59 秒 対 0.7 ミリ秒）。つまり「鍵で比べて、差のあるコマだけ塗る・だけ比べる」が一番効く。
3. 13 本の flow の全コマのうち **63% は、前に流した別の flow のどこかのコマと描く命令まで同じ**（鍵が一致）。比べのコマ 2,058 枚のうち鍵の違う物は 836 枚（41%）。
   同じノードを何度も通る重なりは確かに大きいが、塗りは render-cache が既に 1 回にまとめている。重なりを省いて得するのは、流す（シミュレーション）時間とコピーの時間。
4. JVM 1 本の 9.8〜10.9 GB は **ほぼゴミ**。生きている物は 0.2〜0.3 GB（全コマの World を持っていても）、塗っている間でも 1.8 GB まで。
   `-Xmx2g` で RSS 2.45 GB・遅くならない（2 章の M5）。
5. 順番: **A 鍵の旗（済）→ B ヒープ → C 鍵で比べる（diff）→ D 鍵を先に・塗りは後で → E 常駐で流す → F 前置きを 1 回だけ流して分ける → G ノード単位**。
   A〜D は engine を変えない（Go とテンプレートだけ）。E〜G は engine に口を足すので相談する。

## 1. 目標

物語の長さ 5 倍・分岐 3 倍（flow 13 本 → 約 40 本・1 本 6,600 コマ → 約 33,000 コマ・比べのコマ 2,058 → 約 31,000 枚）を想定する。

| 場面 | 今（血鱗・13 本） | 目標（5 倍 × 3 倍） |
|---|---|---|
| ゲームの .flix を 1 か所直した後の撮り直し + 比べ（描く物が変わったコマ 200 枚以下） | 約 1〜4 分【推】（下の内訳） | **3 分以内** |
| 同じ物をもう 1 回（何も変えずに） | 同上 | **1 分以内** |
| engine を直した後（全部の鍵が変わる・冷えた状態） | 冷えた時 978 秒（3 本ずつ） | **20 分以内** |
| メモリ | 1 本 8 GB の見積もりで本数を絞る | 1 本 2.5 GB 以下・本数は CPU だけで決まる |

「人の目で見る迷った差の頁」の作りと線引き（docs/migrate-diff.md の合格線）は変えない。速くする所は撮る・比べる道だけ。

## 3. 案と効き目

### A. 鍵の JVM の起動旗を絵に効く物だけに（**済**・538c63f5）

- `RenderCache.runtimeId` の「起動旗の全部」を、`RenderCache.paintFlagsOf`（`-Dsun.java2d.*`・`-Dawt.*`・`-Djava.awt.*`・`-Dswing.*`・`-Dsun.font.*` だけ残す）に替えた。
- 効き目: `--jobs` を変える・`-Xmx` を足す・GC の記録を取るだけで、全部のコマ（血鱗 13 本で冷えた時の 978 秒相当）を塗り直していたのが無くなる。B の前提。
- novel-tape-deck.md 1 章の「写しの作業場では 1 回 jar が作り直された（理由は未確認）→ 冷えた」は、jar ではなく旗が変わったためと読める【推】。

### B. JVM のヒープを固定の上限にする（Go の `shoot` だけ）

- `shoot` は今 `-XX:MaxRAMPercentage=60/本数` を渡し、本数を「メモリ 8 GB に 1 本」で絞る。これを **`-Xmx3g`（1 本の上限）** にし、本数は CPU だけで決める。
- 3g の根拠: 生きている物の最大 1.8 GB（M5）+ 長さ 5 倍で World の列が 0.3 → 1.5 GB に増える分の余裕。5 倍の長さで足りなくなったら E（全部の World を持たない）で減らす。
- 効き目: メモリ 1 本 10 GB → 2.5〜3.5 GB。本数を増やせる（ただし冷えた時の塗りは 1 本 7 コアなので、CPU の方が先に埋まる）。
- 見積もり: 0.5〜1 時間（`shoot.go` の旗・`autoJobs`・テスト・docs/migrate-diff.md の 1 行）。

### C. 鍵が同じコマは画素を比べない（Go の `diff` だけ）

- `shootFrames` は既に `frames/<層>/drawhash.txt`（コマの番号 → 鍵）を書いている（VideoOut）。`diff` はこれを読み、tape.json の `frames[].file`（`f0126.png`）の番号で鍵を引く。
- 前と後の鍵が同じなら「同じ」として画素を読まない（鍵が同じなら PNG は 1 バイトも違わない、が DrawHash の約束）。違えば今の画素の比べ。drawhash.txt が無い記録は今まで通り。
- 鍵にはエンジンの fpkg と JVM が入るので、**前の版（古い engine）と新しい版の比べでは鍵は一致しない** → 自動で今の画素の比べに戻る。効くのは「新しい版どうしの退行の確かめ」（移行の後の、毎回の直し）と、同じ engine どうしの移行（ゲームの .flix だけを書き換える移行）。
- 加えて **比べた結果を覚えておく**（`report` の横に `diff-cache.json`: (前の PNG の SHA-256 か鍵, 後の鍵, 線引きの指紋) → 結果）。前と後の engine が違う比べでも、直した後に描く物が変わらなかったコマは画素を読み直さない。
- 効き目: 退行の確かめの diff 14.5 秒 → 1〜2 秒（13 本）・5 倍 × 3 倍で 220 秒 → 10 秒前後【推】。移行の比べも 2 回目から変わったコマの分だけ。
- 見積もり: 3〜4 時間（読み・覚える場所・テスト 6〜8 本・docs/migrate-diff.md）。

### D. 鍵を先に作り、塗る・写すのは差のあるコマだけ（テンプレートと Go）

- 今の `shoot` は比べのコマを全部 PNG で書く（冷えていれば塗る・当たれば写す 1 枚 8 ミリ秒前後）。記録 1 つが 2.3 GB。
- 段 1: flow を流し、比べのコマは **鍵だけ**を書く（テンプレートの `shootFrames` が `FGE_VIDEO_PAINT=none` を受け継げば既に鍵だけになる。今は WhyNot で避けている所を、`MIGRATE_PAINT=keys` の時だけ使う）。
- 段 2: Go が基準の鍵と突き合わせ、鍵の違うコマの番号だけを `FGE_VIDEO_PAINT=frames:A-B,…` で渡してその flow を流し直す（流すのは 1 本 5〜10 秒・差のある flow だけ）。
  頁に並べる絵が要るのは差のあるコマだけなので、同じコマの PNG は書かない（基準の側の PNG を指す）。
- 前の版との比べ（鍵が一致しない）では段 2 が全部のコマになり、今と同じ。退行の確かめで効く。
- 効き目: 退行の確かめでは写すのと PNG の場所がほぼ 0 に（5 倍 × 3 倍で 1 本 6 秒 × 40 本 ≒ 60 秒 / 本数）。差の出た flow だけ 2 回流す。
- engine の変更: なし【推】。`VideoOut.PaintRange.Frames` は既にある。テンプレートの `shootFrames`（paint を受け継ぐかの分かれ道）と Go の 2 段の呼び方。
- 見積もり: 4〜6 時間。

### E. 1 本の常駐の JVM で flow を続けて流す（engine: 小さい口）

- 今は flow ごと・セーブごとに JVM を起こす（13 + 12 回 → 5 倍 × 3 倍で 40 + 36 回）。1 回あたり起動 1.5 秒 + 字と Doc の用意 + JIT が温まるまで。
- `App.Headless` の常駐（`bin/fge resident`・`FlowVideo.jobs`）は既にあり、入口を頼めば同じ JVM で流す。`shoot` を「本数ぶんの常駐に flow を配る」形にする。
- **flow ごとに全部の World の列を持たない**: `Flow.play` は全フレームの World を `outcome#frames` に持って返す（6,583 コマで 0.3 GB・5 倍で 1.5 GB）。
  比べのコマ・音・tape.json に要るのはフレームごとの小さな記録と、撮るフレームの World だけなので、`Flow.play` に「フレームごとに呼ぶ関数」を渡す形（畳み込み）を足すと、生きている物が長さに比例しなくなる。**engine_world の Flow に口を足す（相談）**。
- 効き目: 起動と用意で 40 本 × 3〜4 秒 / 本数 ≒ 30〜40 秒。メモリは長さに依らず 0.3 GB 前後【推】。
- 見積もり: 常駐へ配る 2〜4 時間（Go）・Flow の畳み込みの口 3〜5 時間（engine_world・テスト）。

### F. 共通の前置きを 1 回だけ流して分ける（engine: Flow に口）

- 13 本のうち 7 本（route_* 4 本・tape_* 3 本）は、直に、または `route_to_bones.flow` を通して `run route_to_fork.flow` で始まる（分かれ道までの同じ手順）。うち 5 本はさらに `route_to_bones.flow` まで同じ。分岐が 3 倍になると、同じ前置きを流す回数が増える。
- Flix の World は書き換わらない値なので、**常駐の中で前置きを 1 回流し、その終わりの World をそのまま各 flow の続きの始まりに渡せる**（セーブに書いて読み戻す必要が無い）。
  `Flow.play` は既に `start = { world, state }` を受け取る。足りないのは「手順の列を前置きと続きに分ける」「続きの記録（フレームの番号・時刻・mark）を前置きの後ろへ繋ぐ」口。
- 門: 分けて流した記録の **drawhash.txt と tape.json が、頭から流した物と 1 バイトも違わない**（M6 の鍵の列で比べられる）。違えば分けない（その flow は頭から）。
  入力の手の状態（押したままのキー・`awaiting`）は `run` の切れ目では空になっているはずだが【未確認】、空でない所では分けない。
- 効き目: 流すコマが 13 本で 73,087 → 約 45,000（前置きの重なりだけ）【推】。5 倍 × 3 倍では分岐が増えるほど効く（前置きの長さ × (分岐 − 1)）。
- 見積もり: 6〜10 時間（Flow の口・テンプレート・門のテスト）。**engine_world の Flow に口を足す（相談）**。

### G. ノード（ビート）単位で流して覚える（engine: 大きい）

- 単位 = 「ノードに入る時の World（の指紋）+ 流す入力」から「次のノードに入るまで」。単位ごとに記録（events・コマの鍵・音）を覚え、同じ単位は流さずに記録を繋ぐ。
- M7 の通り、13 本で単位の種類は 56・重なりは 55〜80%。時間が「経路の数」でなく「ノード × 入り方の数」に比例するようになる。
- 難しい所:
  1. **入る時の World の指紋**: World 全体（問いの値だけでなく、舞台・音・揺れの時刻・Timeline の再生位置）を畳む関数が要る。問いの値だけで決めると、M7 の 80% と 55% の差のように、入力の速さが違う単位を取り違える。
  2. **台本・Doc・コードの変更**: コードを直すと、どの単位の振る舞いが変わったかは流さないと分からない。jar が変われば全部の単位を流し直すしかなく、**.flix を直した直後（いちばん多い場面）には効かない**。効くのは台本（.yarn）と Doc だけを直した時（変えたノードとその後ろだけ流し直す）。
  3. 入力: flow の手はノードをまたいで書かれる（`drive viewer until choice`）。単位に切ると、手順の側も単位ごとに切り直す必要がある。
- 既にある物: 決定性の門 `make determinism`（同じ入力から同じ World になる）・`Timeline.PlaybackLog` の seekOn/resumeOn（Timeline の中の頭出し）・セーブ（beat の頭で取る）。
- 判断: **今は作らない**。A〜F の後でも目標に届かない時、または台本だけの直しを数秒で確かめたくなった時に作る。F の「前置きを分ける」が、G の「入り口の World を受け渡す」の小さな版になっている。
- 見積もり: 15〜25 時間（指紋・単位の記録・手順の切り方・門）。

### H. 塗りを GPU（Dawn の画面なし）にする案

- 速さは一番出る（全コマの動画は 6,583 コマを GPU で 55 秒・SoftRaster なら 1 時間弱）。しかし **GL・GPU の絵は鍵の約束の外**（VideoOut の冒頭・docs/design/render-speed.md 3.5 節）で、機械・ドライバで画素が変わる。
  前の版（SoftRaster で撮った基準）と比べると、全部のコマに GPU と SoftRaster の差が出る。
- 前と後の両方を同じ機械の GPU で撮り直すなら比べは成り立つが、基準も撮り直しになり（novel-tape-deck.md 3 章の保存した jar が要る）、門が機械に依る。
- 判断: **門には使わない**。デッキ（差の所をその場で塗って並べる）と人が見る動画に使う。冷えた時の速さは、鍵の重なり（M8: 41%）を並べた JVM どうしで分け合う方で取る（次の I）。

### I. 冷えた時: 並べた JVM どうしで同じ鍵を 2 回塗らない（engine: RenderCache に小さい口）

- 13 本を 3 本ずつ並べると、同じ鍵のコマ（M8: 2,058 枚中 1,222 枚が重複）を別の JVM が同時に塗る事がある（キャッシュに入るのは塗り終えてから）。
- RenderCache に「塗り始める前に鍵の印を原子的に作る（`<鍵>.painting`）・他の JVM の印があれば待って写す」を足す。
- 効き目: 冷えた時の塗りが「比べのコマの数」から「鍵の種類の数」へ（13 本で 2,058 → 836 枚・最大 2.5 倍）【推: 今どれだけ重ねて塗っているかは未計測】。
- 見積もり: 2〜3 時間。**engine_tools の RenderCache を変える（相談）**。

### 効き目のまとめ（5 倍 × 3 倍・ゲームの .flix を 1 か所直した後・描く物の変わったコマ 200 枚）【推】

## 6. テープとデッキ（novel-tape-deck.md）との関係

- デッキ（差の所をその場で塗って並べる）は、**C・D の「鍵の違うコマの一覧」をそのまま頭出しの一覧に使える**。録画が要らないのは D と同じ考え方。

- テープの ② の「前の版の jar を保存」は、前の版を撮り直す時（H を門に使わない限り、基準を撮り直すのは engine を直した時だけ）に要る。この設計の A〜F とは独立に進められる。
- 順: A〜D → デッキの頁（差の所の並び）→ E・F → デッキの再生（常駐から 1 コマずつ）。
